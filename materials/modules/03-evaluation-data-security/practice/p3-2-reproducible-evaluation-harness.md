# П3.2. Воспроизводимый контур оценки

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Собрать воспроизводимые измерения без автоматического выставления зачёта и проверить ограничения судьи.

## Перед началом

П3.1; теория 3, разделы 3–4. Точные метрики исполняются кодом, решение о сдаче принимает человек.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p3-2-reproducible-evaluation-harness/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Результаты benchmark и retrieval; человеческая разметка отдельной калибровочной выборки. Локальный LLM-судья — при его реальной необходимости.

## Порядок самостоятельного выполнения

1. Опишите формат результатов: ID случая, версия системы, outcome, schema_ok, смысловая оценка, latency и ресурсы. Включите транспортные/парсерные ошибки и пустой результат.

2. Исполните точные проверки статуса и расчёт retrieval-метрик. Вручную пересчитайте один случай, например C,B,A при relevant A,B; сопоставьте с кодом. Укажите политику пустого знаменателя и процентиля.

3. Создайте таблицу экспертной проверки: корректность факта, полнота, поддержка источником и отказ. Отметьте, какие колонки допускают автоматическое сравнение, а какие требуют источника и эксперта.

4. Если применяете LLM-судью, закрепите модель/промпт/параметры, сравните с независимой человеческой разметкой. Повторите пары A/B и B/A, краткий/многословный одинаковый ответ; посчитайте согласованность и смену предпочтения. Если судья не нужен, документируйте выбор точных и экспертных проверок и разберите эти bias-сценарии вручную.

5. Подготовьте отчёт по всем случаям, срезам и неопределённости. Другой участник воспроизводит расчёты. Никакой скрипт не назначает участнику зачёт; проверяемость результата поддерживает ручное review.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py metrics
docker compose run --rm lab python scripts/benchmark.py --prompt v2
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Пустой набор, NaN, пропущенное измерение, перефразированный неверный ответ, перестановка порядка. Неизвестное не превращается в успешный результат.

## Самопроверка и критерии приёмки

конфигурация и версии зафиксированы; есть сравнение судьи с человеческой разметкой на отдельной выборке, проверка предвзятости к порядку/стилю и отчёт о расхождениях; решение не опирается только на судью.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

код/конфигурация измерений, построчные результаты, ручной пересчёт, экспертная таблица и калибровка судьи либо обоснование его неприменения.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Если перестановка ответов меняет оценку судьи, report должен показать нестабильность, а не усреднить её незаметно. Судья не проверяет реальное отсутствие записи/утечки.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p3-2-reproducible-evaluation-harness.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
