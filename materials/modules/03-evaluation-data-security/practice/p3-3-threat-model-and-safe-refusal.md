# П3.3. Threat model и безопасный отказ

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Связать угрозу с реальной границей полномочий и продемонстрировать безопасный отказ.

## Перед началом

П3.1; теория 3, разделы 5–6. Только синтетические данные и локальный тестовый контур.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p3-3-threat-model-and-safe-refusal/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`corpus.json`, закрытая для A запись B с canary, `scripts/tools.py`, `scripts/tool_dispatch.py`; выбранный сценарий RAG/документов/tools.

## Порядок самостоятельного выполнения

1. Нарисуйте поток данных и доверенные компоненты: пользователь, IdP/роль, корпус, retrieval, модель, инструменты, БД, журнал. Укажите активы и возможные нежелательные эффекты.

2. Заполните реестр угроз минимум по направлениям: прямая/косвенная injection, poisoning, ACL, exfiltration, логи, SQL/generated code, неподтверждённый write. Для каждого высокого риска назначьте учебного владельца и проверку.

3. Сформулируйте для атак ожидаемый результат до запуска: отсутствие закрытого текста в кандидатах/контексте, отсутствие эффекта без подтверждения, контролируемый отказ и минимальный аудит.

4. Запустите демонстрацию effects и tool_dispatch; предъявите состояние до/после. Для RAG A проверьте состав разрешённых документов до reranker/генератора. Фраза отказа в ответе не заменяет эти доказательства.

5. Проверьте журнал на canary/токен/содержимое. Сформируйте остаточные риски и no-go по непроверенной критичной границе. Сохраните атаки как известные регрессионные случаи.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py effects
docker compose run --rm lab python scripts/tool_dispatch.py
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Документ требует раскрыть B; tool output предлагает write; модель подставляет actor=admin; запрос не содержит подтверждения. Приложение не принимает текст за полномочие.

## Самопроверка и критерии приёмки

рассмотрены инъекции, poisoning, утечки через ответы и логи, ACL, инструменты и generated code/SQL; для каждого высокого риска есть владелец и проверка; продемонстрированы отказ при недопустимом запросе и отсутствие неподтверждённого действия.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

DFD, threat-register.md с владельцами, attack-cases.csv, фактические следы отказов/состояния и решение по остаточным рискам.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Фильтрация финального ответа запаздывает, если закрытый текст уже передан модели. Используйте синтетическую canary, реальные секреты для проверки утечек не нужны.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
