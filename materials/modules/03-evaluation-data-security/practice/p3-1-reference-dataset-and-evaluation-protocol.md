# П3.1. Эталонный набор и протокол оценки

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Подготовить протокол и эталон, на которых можно честно сравнивать изменения.

## Перед началом

Теория 3, разделы 1–4; кейс из П0.1. Доступен второй разметчик в учебной роли.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p3-1-reference-dataset-and-evaluation-protocol/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Открытые status-dev и questions-dev — только примеры формата. Создайте новые группы по сценарию; независимые test-ответы хранит назначенный хранитель.

## Порядок самостоятельного выполнения

1. Определите единицу: карточка статуса, вопрос или документ. Создайте реестр ID, group/family, происхождения, права использования, синтетики, версии, категории и эталона. Приведите штатные, сложные, отсутствующие и запрещённые случаи.

2. Напишите правила разметки с двумя граничными примерами и процедурой эскалации. Два человека независимо размечают общую часть; сохраните обе версии до обсуждения, долю совпадений и причины разногласий.

3. Сначала найдите точные и близкие дубли, затем разделите по семье/проекту/времени. Все производные одного источника остаются в одной группе. Сделайте таблицу group→split и проверьте отсутствие пересечений.

4. Задайте метрики, знаменатели, baseline, целевые пороги и допустимые регрессии. Обоснуйте размер набора через покрытие/неопределённость, а не универсальное число строк. Зафиксируйте всё до финального теста.

5. Передайте test хранителю; разработчику доступны train/dev и схема. Для одиночного прохождения используйте открытый набор как учебную демонстрацию, а независимую проверку запланируйте с коллегой — самоограничение без контроля не делает test независимым.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py metrics
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Почти одинаковые страницы в train/test; эталон test индексируется в RAG; синтетика получена перефразированием test. Перегруппируйте до эксперимента и обновите версию.

## Самопроверка и критерии приёмки

указаны происхождение, права и покрытие типовых/сложных/негативных случаев; тест отделён от данных настройки; определены групповое разделение, размер выборки, пороги и процесс разрешения разногласий экспертов.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Можно ли включить в RAG документ, по которому test задаёт вопрос? Что именно должно оставаться вне индекса?

## Что представить для сверки

dataset manifest, train/dev, ссылка/версия закрытого test без ответов, инструкция разметчика, протокол согласованности и оценки.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Синтетические данные комплекта открыты вместе с решениями; их нельзя называть скрытым независимым test. Небольшой учебный набор подтверждает методику, а не надёжность предприятия.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p3-1-reference-dataset-and-evaluation-protocol.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
