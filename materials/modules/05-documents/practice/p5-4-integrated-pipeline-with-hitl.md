# П5.4. Сводный пайплайн с HITL

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Собрать pipeline и оценить правила HITL через долю ручной проверки и пропущенные ошибки.

## Перед началом

П5.1–П5.3; теория 5, раздел 6. Есть экспертная разметка dev и независимая тестовая выборка.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p5-4-integrated-pipeline-with-hitl/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

OCR/VLM/LLM JSON, `contracts.py::route`, source verification и таблица dev ошибок. Сигналы confidence разного происхождения не смешиваются автоматически.

## Порядок самостоятельного выполнения

1. Опишите workflow: PDF text/OCR → VLM только по диагностике → JSON → schema/предмет/source checks → auto/review/refuse. Для каждого этапа задайте timeout и ограниченный retry.

2. Зафиксируйте жёсткие причины review: критичное поле без подтверждённого источника, конфликт, единица отсутствует, нечитаемый допуск, новый неизвестный шаблон. Эти правила имеют приоритет над confidence.

3. На dev сгруппируйте наблюдаемый сигнал по диапазонам и посчитайте фактическую ошибку. Выберите порог по риску/нагрузке; LLM self-confidence без калибровки не используйте как вероятность.

4. Создайте простую очередь review (локальная CSV/Markdown допустима): ID, причина, разрешённая ссылка/область, решение, роль проверяющего, время. Полный документ и секреты не экспортируются в общий аудит.

5. На test посчитайте manual_fraction, ошибки среди auto-accepted, долю всех ошибок, прошедших мимо проверки, время эксперта и время цикла. Проведите чувствительность экономики к росту review.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py fields
docker compose run --rm lab python scripts/document_pipeline.py
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Высокий confidence при неверном source; эксперт недоступен; очередь переполнена; OCR отказал. Маршрут — review/refuse с понятным статусом, не auto-guess.

## Самопроверка и критерии приёмки

пороги и правила маршрутизации зафиксированы до теста; измерены доля ручной проверки и пропущенные ошибки на экспертной выборке; все критичные поля без подтверждённого источника попадают на проверку; журнал не раскрывает лишние данные.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Как оценить HITL, если проверялись только подозрительные документы и неизвестно число ошибок в auto?

## Что представить для сверки

pipeline/конфигурация правил, калибровочная таблица, очередь и журнал решений, три метрики HITL и экономика проверки.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Ручная доля 0% не означает успех. Если нет надёжного dev-сигнала, эталон route отправляет всё на review; это честный baseline, который может привести к no-go экономики.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
