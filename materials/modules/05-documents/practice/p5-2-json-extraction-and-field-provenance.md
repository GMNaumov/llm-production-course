# П5.2. Извлечение JSON и происхождение полей

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Извлечь проверяемый JSON, отличая пропуск, нечитаемость и конфликт.

## Перед началом

П5.1; теория 5, раздел 4. Pydantic 2; эталон `contracts.py` показывает один тип поля, контракт спецификации расширяет участник.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p5-2-json-extraction-and-field-provenance/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

OCR text/TSV и оригиналы двухстраничных спецификаций; source включает документ, редакцию, PDF-страницу и bbox при наличии.

## Порядок самостоятельного выполнения

1. Опишите JSON Schema/Pydantic для статуса, обозначения и позиций: position, quantity, unit, state и source. Определите обязательные/критичные поля и правила null до извлечения.

2. Реализуйте baseline-парсер либо вызов LLM по OCR-контексту. Используйте StatusField/extract_status как пример, но дополните позиции и количества. Не подставляйте 0/шт. при отсутствии источника.

3. Для каждого принятого значения сохраните provenance. Переведите bbox TSV из пикселей в нормированные координаты исходной ориентированной страницы; при crop учтите смещение/масштаб.

4. Проверьте существование разрешённого документа/редакции/страницы и визуальное совпадение значения в области. Схема проверяет форму ссылки, а не её истинность. Сохраните результат проверки отдельно от model confidence.

5. Посчитайте precision/recall по каждому обязательному и критичному полю, пропуски, неверные и выдуманные значения. Все автоматически принятые JSON проходят схему; сомнительные поля направьте на ручную проверку и сохраните сырой синтетический ответ для разбора.

## Негативные случаи

Неверный page/bbox; лишнее поле; NaN/Infinity количества; value при unreadable; одна позиция с двумя количествами; документ без единицы.

## Самопроверка и критерии приёмки

все принятые результаты соответствуют схеме; точность и полнота измерены отдельно по обязательным и критичным полям; для критичных значений сохранены документ, страница и, где возможно, координаты; нечитаемые значения не подставляются автоматически.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Если результат не получается

`strict=True` не исправляет смысл. В JSON bbox приходит как массив: используйте model_validate_json или явное согласованное преобразование, а не ослабляйте все типы ради удобства.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
