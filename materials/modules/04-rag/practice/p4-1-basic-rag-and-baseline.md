# П4.1. Базовый RAG и baseline

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Построить RAG с настоящими embeddings и измерить его относительно обычного поиска.

## Перед началом

П3.1–П3.3; теория 4, разделы 1–5. Подготовлен GPU-профиль с chat и multilingual-e5-small; доступ к предприятию не требуется.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p4-1-basic-rag-and-baseline/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`data/corpus.json`, `questions-dev.json`, `scripts/rag.py`. Каждый короткий фрагмент уже содержит документ/редакцию/страницу; это стартовый корпус, а не реалистичный объём.

## Порядок самостоятельного выполнения

1. Составьте manifest корпуса и зафиксируйте его границу, версию, права A/B и правила действующей редакции. Не помещайте questions-dev, must и relevance labels в индекс.

2. Запустите lexical baseline. Затем получите реальные E5 embeddings с правильными query:/passage: префиксами и сравните точный dense-поиск на том же корпусе и вопросах. Для маленького набора точный numpy-поиск достаточен; ANN добавляется только как исследование.

3. Добавьте 2–3 синтетических длинных регламента и реализуйте структурное разбиение по разделам: metadata, chunk_id, версия, страница и checksum сохраняются. На dev сравните два размера фрагмента; убедитесь, что условие и единица не отделились от значения.

4. Соберите top-k разрешённых источников, вызовите генерацию и проверьте схему/существование ID цитат. Вручную проверьте, что каждая цитата действительно поддерживает утверждение. Отсутствие источника ведёт к abstain.

5. Измерьте Recall@k, MRR, качество ответов/отказов, P95, ресурсы и время инженера с проверкой ссылок. Закрепите выбранный вариант на dev и один раз проверьте на новых вопросах, подготовленных коллегой.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/rag.py --mode lexical
docker compose run --rm lab python scripts/rag.py --mode dense --answers
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Нет подходящего документа, устаревшая редакция, точный артикул, закрытый B, конфликт источников. Dense top-k сам по себе не доказывает наличие ответа.

## Самопроверка и критерии приёмки

сервис воспроизводится; ответы содержат ссылки на страницу/фрагмент; на фиксированном наборе измерены Recall@k и MRR, качество ответов и P95 latency; результаты разобраны по типам запросов, включая термины, сокращения и артикулы.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

корпус/manifest, chunker, код сервиса и запросов, retrieval/answer отчёты, экспертные цитаты и сравнение с поиском без генерации.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

В комплекте lexical на пяти ответных dev-вопросах может получить 1,0: это не обещание для предприятия и не основание искусственно ухудшать baseline. Улучшение RAG может заключаться в полезной сводке, но это нужно измерить.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p4-1-basic-rag-and-baseline.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
