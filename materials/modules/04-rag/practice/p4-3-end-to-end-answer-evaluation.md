# П4.3. Сквозная оценка ответов

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Оценить ответ целиком: правильность, полноту, поддержку цитатами и отказ.

## Перед началом

П4.1–П4.2; теория 4, раздел 5, методика экспертов/судьи из модуля 3.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p4-3-end-to-end-answer-evaluation/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`answers-*.json`, исходные документы и вопросы. Подготовьте отдельные варианты пустого, противоречивого и устаревшего retrieval в копии корпуса.

## Порядок самостоятельного выполнения

1. До оценки создайте рубрику с отдельными колонками: верный факт, полнота нужных пунктов, каждое утверждение подтверждено, цитата ведёт на нужную редакцию/страницу, отказ корректен. Не сводите всё к одному красивому score.

2. Выполните генерацию на фиксированных вопросах. Автоматически проверьте схему и ID цитат, затем вручную сопоставьте утверждения с фрагментами. Укажите число просмотренных ответов и правило отбора.

3. Для запроса перед выпуском потребуйте обозначение, количество и единицу. Ссылка на правильную страницу при ответе только об обозначении даёт неполноту, а не полный успех.

4. Запустите негативные варианты: пустой корпус, две действующие противоречивые редакции, только устаревшая запись, недоступный источник. Определите правило актуальности до проверки; при неразрешимом конфликте нужен abstain/эксперт.

5. Посчитайте coverage, ошибочные ответы, избыточные отказы и качество среди отвеченных вместе с общим знаменателем. Если нужен judge, примените калибровку П3.2 и сохраните экспертную проверку критичных случаев.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/rag.py --mode lexical --answers
# Варианты корпуса создавайте в своей копии, сохраняя исходный manifest.
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Отдельно проверьте ответ провайдера с `choices=[]`, `content=null` и сгенерированные `null`, список и объект с неверным типом `state`. Прогон должен сохранить каждый случай. Ошибку зависимости учитывайте отдельно от отказа по недостатку источников; она остаётся в общем знаменателе. Подставные ответы проверяют контракт, но не качество модели.

Существующая ссылка не подтверждает вывод; модель подмешивает знание вне контекста; отказывается от всех вопросов; молча выбирает одну из противоречащих версий.

## Самопроверка и критерии приёмки

использованы автоматические проверки и экспертная выборка; LLM-as-judge, если применяется, откалиброван по П3.2; есть отдельные результаты на пустом, противоречивом и устаревшем retrieval.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

рубрика и построчная экспертная таблица, отчёт с отдельными срезами, негативные входы и ожидаемые/фактические результаты.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

must в открытом dev — подсказка для рубрики, а не универсальный keyword judge: слово «запрещено» может стоять в неверном контексте. Проверяйте смысл.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p4-3-end-to-end-answer-evaluation.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
