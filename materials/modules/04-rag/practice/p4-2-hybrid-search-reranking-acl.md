# П4.2. Гибридный поиск, reranking и ACL

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Проверить добавочную пользу hybrid/reranker и отсутствие передачи закрытых источников модели.

## Перед началом

П4.1, теория 4, разделы 3–4 и 6. Локально доступен pretrained reranker; сравнение идёт на неизменной выборке.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p4-2-hybrid-search-reranking-acl/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Зафиксированные вопросы/корпус П4.1, запись B с canary, RRF в `scripts/rag.py`, `/rerank` локального model_server.

## Порядок самостоятельного выполнения

1. Сохраните lexical и dense результаты П4.1. Зафиксируйте k, ширину кандидатного пула и RRF constant до финального сравнения; настройка допускается только на dev.

2. Запустите hybrid и rerank. Ранжируйте один и тот же разрешённый top-N, не добавляя релевантный документ из эталона вручную. Считайте Recall@k, MRR/nDCG и добавочную latency.

3. Разберите каждый изменившийся порядок: синоним, артикул, отрицание, редакция. Если relevant нет в top-N, классифицируйте ошибку retrieval; reranker не может её исправить.

4. Проверьте пользователя A, B и неизвестную личность. До dense/rerank/генерации зафиксируйте ID разрешённых кандидатов; в сервисе личность берётся из серверного контекста, не из текста запроса.

5. Проверьте прямой запрос canary, косвенную injection и отзыв прав между поиском и ответом. Повторная проверка политики до выдачи обязательна при изменяемых правах. Обоснуйте, стоит ли оставлять усложнение.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/rag.py --mode hybrid
docker compose run --rm lab python scripts/rag.py --mode rerank
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Пользователь просит изменить plant в вопросе; ranking B попадает в общий cache; relevant отсутствует в пуле; reranker хуже готового baseline. Усложнение не обязано победить.

## Самопроверка и критерии приёмки

на неизменном наборе сравнены Recall@k, MRR, nDCG и latency; ACL применяется до retrieval и генерации; все тесты на доступ к чужим документам пройдены без утечки; отсутствие улучшения от усложнения зафиксировано без подгонки данных.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Если результат не получается

Реализация точного поиска фильтрует корпус до кодирования. При переносе в pgvector/Qdrant отдельно проверьте фактический query plan и recall фильтрации; наличие WHERE не доказывает полноту ANN.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
