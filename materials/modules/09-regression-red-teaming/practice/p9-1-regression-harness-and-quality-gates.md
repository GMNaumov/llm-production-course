# П9.1. Регрессионный контур и quality gates

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Собрать известные регрессии в прозрачное ручное решение о допуске выпуска.

## Перед началом

П3.2 и работы выбранного сценария; теория 9, разделы 1–3. Автоматические расчёты разрешены как инженерный инструмент, автоматического оценивания учебных работ нет.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p9-1-regression-harness-and-quality-gates/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Известные случаи статусов/RAG/OCR/tools, benchmark/retrieval отчёты, `demo.py::gate`. Пороги в демонстрации условны и не задают норм предприятия.

## Порядок самостоятельного выполнения

1. Составьте matrix случай→инвариант→метод→версия→владелец: качество, корректный отказ, schema, права, эффект, latency и ресурс. Разделите точные расчёты и экспертные оценки.

2. До финального прогона закрепите threshold/направление/допустимую регрессию, минимальный объём/покрытие и исход insufficient evidence. Критичная утечка/неподтверждённый write блокируют выпуск независимо от среднего качества.

3. Соберите единый release report из построчных результатов. Проверьте пропущенные измерения, пустую выборку, NaN/Infinity и несовместимую версию набора. Эти случаи не получают pass.

4. В тестовой копии намеренно внесите одну регрессию: неверный unknown, старая редакция или отсутствие проверки source. Покажите, что соответствующая проверка/эксперт обнаруживает её и меняет решение.

5. Верните исправление, повторите исходный и штатный наборы. Человек подписывает решение с ограничениями; скрипт gate не ставит участнику оценку и не заменяет независимый test новых возможностей.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py gates
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Нет p95, quality=NaN, отсутствует ACL-run, хороший средний score при одной утечке, известный regression выдан за независимый test.

## Самопроверка и критерии приёмки

пороги и недопустимые регрессии зафиксированы до финального прогона; проверки охватывают качество, отказы, latency и права; автоматические и экспертные оценки разделены; продемонстрировано обнаружение намеренно внесённой регрессии.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Почему insufficient evidence нельзя автоматически трактовать как pass?

## Что представить для сверки

regression matrix, версия порогов, release report до/после регрессии, экспертный протокол и ручное решение.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Знакомые случаи полезны для регрессий, но не подтверждают перенос. Перенос порогов из demo без связи с риском не выполняет задание.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
