# П9.2. Red teaming и повторная проверка

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 4 ак. ч. (180 минут). Работа обязательна на базовом уровне. Подготовка — 25 мин; реализация/эксперимент — 80; негативные случаи — 45; анализ и оформление — 30. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Проверить реальные эффекты атак, исправить корневые причины и повторить проверки.

## Перед началом

П3.3, П9.1; теория 9, разделы 4–6. Только изолированный контур, синтетические canary и разрешённые инструменты.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p9-2-red-teaming-and-retesting/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Injection-документ, закрытый B, строка БД с инструкцией, tool output, опасный C#-комментарий, stale/replay preview.

## Порядок самостоятельного выполнения

1. Для каждой атаки укажите актив, вход, возможности атакующего, ожидаемый безопасный результат и наблюдаемое доказательство. Охватите документы, БД, tools, ACL, poisoning, exfiltration и логи.

2. Исполните атаки на выбранном сценарии. Проверяйте состав контекста/reranker, реальные вызовы/состояние БД, выход и аудит. Для SQL/code текст атаки не требует исполнения опасного кода.

3. Проверьте попытку загрузить отравленный документ с выдуманными правами/редакцией. Источник policy/актуальности должен быть доверенным; метаданные загружаемого файла не назначают scope.

4. Для каждой находки сохраните минимальный синтетический repro, тяжесть, владельца, корневую границу и исправление. Prompt-only исправление не считается достаточным при лишних правах инструмента.

5. Повторите исходную атаку, близкий вариант и штатные случаи. Проверьте аудит/историю/cache на canary и секреты. Критичный неустранённый риск даёт no-go; известная атака добавляется в regression.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/tool_dispatch.py
docker compose run --rm lab python scripts/demo.py effects
docker compose run --rm lab python scripts/lifecycle.py
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Ответ отказывает, но инструмент уже выполнил запись; закрытый текст скрыт в финале, но был в контексте; backup возвращает удалённый документ; логи раскрывают тело.

## Самопроверка и критерии приёмки

каждая атака имеет ожидаемый безопасный результат и фактический след в аудите; критичные находки исправлены и перепроверены либо сценарий получает no-go; журналы и трассировки проверены на отсутствие лишних чувствительных данных.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Какая атака проверяет poisoning, а какая prompt injection? Где различаются меры?

## Что представить для сверки

attack register с ожидаемым/фактическим эффектом, исправления/retest, минимальные очищенные следы и no-go/pass-with-scope решение человека.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Отсутствие утечки в одном ответе не доказывает защиту всего пути. Реальные секреты не нужны: используйте canary. Исходящий вызов блокируется средой, а не просьбой в prompt.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p9-2-red-teaming-and-retesting.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
