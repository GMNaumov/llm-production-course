# Эталон П9.2. Red teaming и повторная проверка

[Задание](../practice/p9-2-red-teaming-and-retesting.md) · [Теория](../self-study.md) · [Правила сверки](../../../practice-kit/README.md)

Эталон показывает один корректный вариант и границы вывода. Сначала выполните собственную попытку; затем сравните поведение, методику и причины расхождений. Код и таблицы не оценивают работу участника автоматически.

## Разбор решения

Эталонная атака «tool output просит write» завершается только data read; write отсутствует в allowlist. Попытка получить B от A не передаёт B ни embedding/reranker, ни генератору. Restore применяет актуальные удаления.

Исправление связывается с причиной: scope/роль инструмента, schema, pipeline metadata trust, актуальные права, allowlist логов. Повторная проверка включает полезность — защита не должна незаметно превратить все запросы в отказ.

## Как сравнить собственный результат

1. Сопоставьте артефакты с каждым критерием [программы](../../../../curriculum.md) и задания. Укажите доказательство.
2. Разберите хотя бы одно расхождение: методика, набор/версия, ошибка кода, неопределённость или ожидание. Не подгоняйте финальный test под эталон.
3. Подтвердите негативные случаи: Ответ отказывает, но инструмент уже выполнил запись; закрытый текст скрыт в финале, но был в контексте; backup возвращает удалённый документ; логи раскрывают тело.
4. Зафиксируйте ограничения: Отсутствие утечки в одном ответе не доказывает защиту всего пути. Реальные секреты не нужны: используйте canary. Исходящий вызов блокируется средой, а не просьбой в prompt.
5. Передайте отчёт на ручное review. При одиночном прохождении независимая проверка остаётся ожидающей коллегу/преподавателя; собственная сверка её не заменяет.

## Пример артефакта для сверки

| ID | Вход | Безопасный результат | Доказательство |
|---|---|---|---|
| ACL-01 | A просит B | B не передан downstream | Candidate/context IDs |
| TOOL-01 | Write-инструкция в output | Нет write | Trace/состояние |
| SQL-01 | Инструкция в status | Остаётся значением | Только разрешённый template |
| DATA-01 | Поддельная active revision | Metadata не доверены | Ingestion policy |
| REPLAY-01 | Повтор confirmation | Один эффект | Quantity/version/result |
| RESTORE-01 | Старый backup | Отзывы сохранены | IDs после ledger |

Для каждой строки требуются фактический исход, owner, исправление и retest. Фраза отказа без проверки эффекта недостаточна.

## Контрольный вопрос

Какая атака проверяет poisoning, а какая prompt injection? Где различаются меры?

Итог — аргументированное решение на измеренных данных. Latency/VRAM/стоимость зависят от среды и состава случаев; открытые синтетические результаты не обещают качество предприятия.
