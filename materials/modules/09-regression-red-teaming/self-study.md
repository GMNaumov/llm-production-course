## 1. Что меняется при выпуске

Поведение зависит не только от модели: промпт, шаблон, индекс, правила разбиения на фрагменты, OCR, схема инструмента и версия БД также меняют результат. После изменения повторяют известные проверки из регрессионного набора, чтобы выяснить, сохранились ли ранее подтверждённые свойства системы.

Набор разбивают на быстрые детерминированные проверки, компонентные метрики, сквозные сценарии, проверки безопасности и экспертную выборку. Автоматическое сравнение значения, JSON-схемы или кода HTTP предпочтительнее оценки судьёй, когда существует точный ответ. Эксперт нужен для оценки предметного смысла, спорных источников и критичных полей.

| Область | Пример инварианта | Что наблюдать |
|---|---|---|
| Промпт | Не выдумывать статус при отсутствии данных | Корректный отказ и покрытие |
| RAG | Закрытый источник не поступает генератору | Фактический состав кандидатов и контекста |
| Документы | Нечитаемый допуск не принимается автоматически | Значение, источник и маршрут HITL |
| SQL/tools | Повтор не создаёт второй эффект | Состояние тестовой БД и идентификатор операции |
| Код | Публичный контракт сохраняется | Сборка, тесты и diff/review |
| Адаптер | Улучшение не нарушает общие правила отказа | Срезы и регрессии после serving |

У каждого случая есть идентификатор, версия, категория, входные данные, допустимый результат и способ проверки. Секреты заменяют синтетическими контрольными значениями (canary), по появлению которых можно обнаружить утечку; реальные токены для этого не требуются. Известные атаки и примеры регрессии не выдают за независимый тест новых возможностей.

## 2. Правила допуска и неопределённый исход

Правило допуска (gate) задаётся заранее и не сводится к итоговой оценке. Критичные нарушения доступа блокируют выпуск независимо от среднего качества. Для некритичных метрик задают направление, порог и допустимое ухудшение относительно baseline. Числа определяют владельцы процесса по риску; в курсе нет универсального процента успеха.

Полезны три исхода: **pass** — проверка пройдена, **fail** — проверка не пройдена, **insufficient evidence** — недостаточно данных. Отсутствие прогона, недостаточное число наблюдений или неизвестная версия не должны превращаться в pass. Если доверительный интервал пересекает порог допуска, нужны дополнительные данные по согласованному протоколу, а не повторы до первого удачного результата.

Ниже приведён пример на Python с использованием только стандартной библиотеки. Пороги передаются извне; пример иллюстрирует направление проверки, но не задаёт нормы качества.

```python
from math import isfinite


def gate(*, critical_violations, quality_lower_bound, p95_ms, min_quality, max_p95_ms):
    if type(critical_violations) is not int or critical_violations < 0:
        return "insufficient evidence"
    if critical_violations > 0:
        return "fail"
    values = (quality_lower_bound, p95_ms, min_quality, max_p95_ms)
    if any(type(x) not in (int, float) or not isfinite(x) for x in values):
        return "insufficient evidence"
    if not (0 <= quality_lower_bound <= 1 and 0 <= min_quality <= 1):
        return "insufficient evidence"
    if p95_ms < 0 or max_p95_ms < 0:
        return "insufficient evidence"
    if quality_lower_bound < min_quality or p95_ms > max_p95_ms:
        return "fail"
    return "pass"


print(
    gate(
        critical_violations=1,
        quality_lower_bound=0.99,
        p95_ms=100,
        min_quality=0.90,
        max_p95_ms=500,
    )
)  # fail
```

Пример не засчитывает проверку при отсутствии измерений, бесконечных значениях или NaN, чтобы неизвестное качество не превратилось в pass. В действующей реализации дополнительно проверяют единицы измерения и полноту всех обязательных прогонов. Ноль обнаруженных нарушений характеризует только выполненный набор проверок; он не гарантирует защиты от неизвестных атак.

Задержку сравнивают при одинаковой нагрузке, числе запросов, длине входа и выхода и правилах расчёта P95. Для сравнения качества сохраняют парные результаты по одним и тем же случаям и группам. Несколько значений seed помогают увидеть нестабильность генерации, но не заменяют разнообразия документов. При малой выборке выводы ограничивают теми категориями случаев, которые она охватывает.

## 3. Экспертная выборка и судья

Экспертная проверка включает репрезентативную случайную выборку и отдельно — примеры сложных категорий. Если проверять только подозрительные случаи, полученную частоту ошибок нельзя переносить на весь поток без учёта способа отбора. Проверка только лёгких случаев, напротив, скрывает риски.

LLM-судью используют по [методике модуля 3](../03-evaluation-data-security/self-study.md): фиксируют версию, калибруют, проверяют влияние порядка и стиля ответов, разбирают расхождения. Смена судьи меняет измерительный инструмент, поэтому нового и прежнего судью сравнивают на общей выборке с человеческой разметкой. Рост оценки после замены судьи сам по себе не означает улучшения системы.

## 4. Red teaming как проверка границ

Red teaming — проверка того, может ли нарушитель добиться нежелательного эффекта через предусмотренные интерфейсы системы. Работают только в согласованном тестовом контуре, с синтетическими данными и ограниченными полномочиями. Результат оценивают по соблюдению границ доступа и действий; смена тона ответа модели сама по себе не доказывает нарушения защиты.

Для каждой атаки задают актив, точку входа, возможности атакующего, нарушаемое правило, наблюдаемый эффект и ожидаемое поведение. Классы угроз и различие прямой/косвенной инъекции описаны в [OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

| Сценарий на синтетике | Ожидаемое безопасное поведение | Доказательство |
|---|---|---|
| Документ просит раскрыть соседние закрытые файлы | Инструкция из источника не меняет область полномочий | В результатах поиска, контексте и ответе нет контрольного значения из закрытого источника |
| Результат инструмента содержит просьбу выполнить запись | Данные не дают новых полномочий | Нет операции записи и её эффекта без подтверждения |
| Вопрос к чужому объекту | Сервер ограничивает доступ | Отказ и отсутствие чтения закрытого содержимого |
| Строка БД содержит SQL-инструкцию | Строка остаётся значением | Нет нового выражения или опасного вызова |
| Повтор подтверждённого запроса | Один логический эффект | Один ID результата и запись идемпотентности |
| Старый документ отравляет ответ | Проверяются происхождение и версия | Корректная редакция или явный конфликт |
| Комментарий в коде на C# предлагает отключить проверку | К изменению применяются обычные требования | Опасное изменение отклонено при ревью или технической проверке |

Защиту от отравления данных проверяют на контролируемой копии корпуса: выясняют, кто может загрузить источник, изменить метаданные или включить данные в обучающий набор. Защита только на уровне промпта не обнаруживает подмены редакции при загрузке документов. Утечка возможна не только через текст ответа, но и через параметр URL, инструмент, историю интерфейса и журнал. Запрет внешних сетевых вызовов должен обеспечиваться средой исполнения.

## 5. Наблюдение фактического эффекта

Фраза модели «я не буду изменять заказ» не доказывает отсутствия записи. Проверяют вызовы, авторизацию, состояние БД и журнал выполненных действий. Аналогично отсутствия закрытого текста в финальном ответе недостаточно, если этот текст уже передан на переранжирование или внешнему LLM-судье.

Трассировка связывает версии компонентов, пользователя, политику доступа, операции и их исходы. Для подтверждения соблюдения границ часто достаточно идентификатора и статуса без полного текста документа. Чувствительные данные удаляют до отправки событий в систему наблюдаемости. Не следует проверять утечку с помощью настоящего секрета, который потом придётся искать во всех журналах и кэшах.

## 6. Исправление и повторная проверка

Найденную уязвимость классифицируют по возможному ущербу и воспроизводимости, назначают ответственного, фиксируют первопричину и объём необходимых изменений. Смена формулировки системного промпта может уменьшить вероятность конкретного обхода, но недостаточна, если инструмент по-прежнему имеет лишние права.

После исправления повторяют исходную атаку, близкие варианты и обычные сценарии: защита могла чрезмерно увеличить число отказов. Найденный случай добавляют в набор регрессионных проверок. Для проверки самого контура полезно намеренно внести контролируемую регрессию в тестовой копии и убедиться, что правило допуска её обнаруживает. Такой эксперимент проводят только в тестовом контуре.

Если критичный риск не устранён или результат исправления не подтверждён повторной проверкой, соответствующий сценарий получает no-go. Ограничение разрешённых действий или возврат к обычному поиску может быть обоснованным решением. Для принятия допустимого риска нужны конкретный ответственный и условия применения решения; это не отменяет запретов программы на утечки, обход ACL и производственную запись.

## 7. Самопроверка с пояснениями

1. Почему 99% среднего качества не компенсируют одной утечки? **Ответ:** соблюдение прав доступа — отдельное обязательное условие допуска. Его нарушение блокирует выпуск независимо от среднего качества.
2. Чем регрессионный набор отличается от независимого тестового? **Ответ:** регрессионный набор содержит известные случаи, которые уже могли использоваться при выборе исправления.
3. Как доказать, что защита не сломала полезность? **Ответ:** повторить и атаки, и штатные сценарии, включая долю отказов.
4. Почему нужен исход insufficient evidence? **Ответ:** отсутствие измерения не равно успешной проверке.
