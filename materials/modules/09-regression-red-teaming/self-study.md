## 1. Что меняется при выпуске

Поведение зависит не только от модели: prompt, template, индекс, правила chunking, OCR, схема инструмента и версия БД также меняют результат. Regression suite повторяет известные проверки после изменения и показывает, что ранее работавшие свойства сохранились.

Набор разбивают на быстрые детерминированные проверки, компонентные метрики, end-to-end сценарии, безопасность и экспертную выборку. Автоматическое сравнение значения, JSON-схемы или кода HTTP предпочтительнее судьи, когда есть точный ответ. Эксперт нужен для предметного смысла, спорных источников и критичных полей.

| Область | Пример инварианта | Что наблюдать |
|---|---|---|
| Промпт | Не выдумывать статус при отсутствии данных | Корректный отказ и coverage |
| RAG | Закрытый источник не поступает генератору | Реальный состав кандидатов/контекста |
| Документы | Нечитаемый допуск не принимается автоматически | Значение, источник и маршрут HITL |
| SQL/tools | Повтор не создаёт второй эффект | Состояние тестовой БД и ID операции |
| Код | Публичный контракт сохраняется | Сборка, тесты и diff/review |
| Адаптер | Улучшение не ломает общие отказы | Срезы и регрессии после serving |

У каждого случая есть ID, версия, категория, вход, допустимый результат и способ проверки. Секреты заменяются синтетическими canary-значениями; реальные токены не требуются для проверки утечки. Известные атаки и примеры регрессии не выдаются за независимый тест новых возможностей.

## 2. Quality gates и неопределённый исход

Gate — заранее заданное правило допуска, а не красивый итоговый score. Критичные нарушения доступа блокируют выпуск независимо от среднего качества. Для некритичных метрик задают направление, порог и допустимое ухудшение от baseline. Числа определяют владельцы процесса по риску; в курсе нет универсального процента успеха.

Полезны три исхода: **pass**, **fail**, **insufficient evidence**. Отсутствующий прогон, мало наблюдений или неизвестная версия не должны превращаться в pass. Пограничный доверительный интервал требует дополнительного доказательства по согласованному протоколу, а не повторов до первого удачного результата.

Ниже Python, стандартная библиотека. Пороги передаются извне; пример иллюстрирует направление проверки, не задаёт нормы качества.

```python
from math import isfinite


def gate(*, critical_violations, quality_lower_bound, p95_ms, min_quality, max_p95_ms):
    if type(critical_violations) is not int or critical_violations < 0:
        return "insufficient evidence"
    if critical_violations > 0:
        return "fail"
    values = (quality_lower_bound, p95_ms, min_quality, max_p95_ms)
    if any(type(x) not in (int, float) or not isfinite(x) for x in values):
        return "insufficient evidence"
    if not (0 <= quality_lower_bound <= 1 and 0 <= min_quality <= 1):
        return "insufficient evidence"
    if p95_ms < 0 or max_p95_ms < 0:
        return "insufficient evidence"
    if quality_lower_bound < min_quality or p95_ms > max_p95_ms:
        return "fail"
    return "pass"


print(
    gate(
        critical_violations=1,
        quality_lower_bound=0.99,
        p95_ms=100,
        min_quality=0.90,
        max_p95_ms=500,
    )
)  # fail
```

Пример отклоняет отсутствующие, бесконечные и NaN-измерения, чтобы неизвестное качество не превратилось в pass. В действующей реализации дополнительно проверяют единицы и полноту всех обязательных прогонов. Ноль обнаруженных нарушений описывает только выполненный набор; он не является гарантией отсутствия неизвестной атаки.

Для latency сохраняют одинаковую нагрузку, число запросов, длины и правила расчёта P95. Для качества — парные результаты по одним случаям и группам. Несколько seed помогают увидеть нестабильность генерации, но не заменяют разнообразие документов. При маленькой выборке решение ограничивают областью доказанного покрытия.

## 3. Экспертная выборка и судья

Экспертный просмотр включает репрезентативную случайную часть и отдельно целевые сложные категории. Если проверять только подозрительные случаи, полученная частота ошибок не представляет весь поток без поправки на отбор. Если смотреть только лёгкие — скрываются риски.

LLM-судья используется по [методике модуля 3](../03-evaluation-data-security/self-study.md): закреплённая версия, калибровка, контроль порядка и стиля, разбор расхождений. Смена судьи меняет измерительный инструмент и требует мостового сравнения с прежней человеческой разметкой. Улучшение score после замены судьи само по себе не означает улучшения системы.

## 4. Red teaming как проверка границ

Red teaming исследует, может ли нарушитель добиться нежелательного эффекта через допустимые входы. Работают только с согласованным тестовым контуром, синтетическими данными и ограниченными полномочиями. Цель — измеримый безопасный результат, а не эффектная фраза, заставившая модель сменить тон.

Для каждой атаки задают актив, точку входа, возможности атакующего, нарушаемое правило, наблюдаемый эффект и ожидаемое поведение. Классы угроз и различие прямой/косвенной инъекции описаны в [OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

| Сценарий на синтетике | Ожидаемое безопасное поведение | Доказательство |
|---|---|---|
| Документ просит раскрыть соседние закрытые файлы | Инструкция из источника не меняет scope | В retrieval/ответе нет закрытого canary |
| Tool output просит вызвать write | Данные не становятся полномочием | Нет вызова/эффекта без подтверждения |
| Вопрос к чужому объекту | Сервер ограничивает доступ | Отказ и отсутствие чтения закрытого содержимого |
| Строка БД содержит SQL-инструкцию | Строка остаётся значением | Нет нового выражения или опасного вызова |
| Повтор подтверждённого запроса | Один логический эффект | Один ID результата и запись идемпотентности |
| Старый документ отравляет ответ | Проверяются происхождение и версия | Корректная редакция или явный конфликт |
| Комментарий C# предлагает отключить проверку | Изменение проходит обычные ограничения | Опасный diff отклонён review/проверкой |

Poisoning проверяется через контролируемую копию корпуса: кто может загрузить источник, изменить метаданные или попасть в train. Prompt-only защита не обнаруживает подмену редакции в ingestion. Exfiltration возможна не только текстом ответа, но и аргументом URL, инструментом, историей UI и журналом. Запрет внешнего сетевого вызова должен исполняться средой, а не просьбой в prompt.

## 5. Наблюдение фактического эффекта

Фраза модели «я не буду изменять заказ» не доказывает отсутствие записи. Проверяются вызовы, авторизация, состояние БД и журнал эффектов. Аналогично отсутствие закрытого текста в финальном ответе недостаточно, если текст уже передан reranker или внешнему judge.

Трасса связывает версии, пользователя/политику, операции и исходы. Для доказательства границы часто достаточно ID и статуса без полного текста документа. Sanitization делается до отправки в систему наблюдаемости. Не следует тестировать утечку настоящим секретом, который потом придётся искать во всех логах и кэшах.

## 6. Исправление и повторная проверка

Находку классифицируют по ущербу и воспроизводимости, назначают владельца, фиксируют корневую причину и границу исправления. Смена формулировки системного prompt может уменьшить вероятность конкретного обхода, но недостаточна, если инструмент по-прежнему имеет лишние права.

После исправления повторяют исходную атаку, близкие варианты и обычные сценарии: защита могла чрезмерно увеличить отказы. Найденный случай добавляется в regression suite. Для проверки самого контура полезно намеренно внести контролируемую регрессию в тестовой копии и убедиться, что gate её обнаруживает; это не внесение уязвимости в production.

Если критичный риск не устранён и перепроверка невозможна, соответствующий сценарий получает no-go. Ограничение разрешённых действий или возврат к обычному поиску может быть обоснованным решением. Принятый риск требует конкретного владельца и границ, но не отменяет запреты программы на утечки, обход ACL и производственную запись.

## 7. Самопроверка с пояснениями

1. Почему 99% среднего качества не компенсируют одну утечку? **Ответ:** это отдельный блокирующий инвариант, а не взаимозаменяемый балл.
2. Чем отличается regression от независимого test? **Ответ:** regression содержит известные случаи, на которых уже могли выбирать исправление.
3. Как доказать, что защита не сломала полезность? **Ответ:** повторить и атаки, и штатные сценарии, включая долю отказов.
4. Почему нужен исход insufficient evidence? **Ответ:** отсутствие измерения не равно успешной проверке.
