# П8.3. Embedding или reranker

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Выбрать и дообучить один retrieval-компонент по фактической ошибке.

## Перед началом

П4.1–П4.2, П8.1; теория 8, раздел 7. Программа требует embedding ИЛИ reranker, не оба.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p8-3-embedding-or-reranker/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Диагностика retrieval, pretrained сильный baseline, локальный reranker snapshot. `train_reranker.py` — исполняемый пример на четырёх открытых парах, не достаточный набор эксперимента.

## Порядок самостоятельного выполнения

1. На dev измерьте, есть ли relevant в широком top-N. Если нет — исследуйте ingestion/ACL/embedding; если есть, но низко — выбирайте reranker. Зафиксируйте одно изменение и готовый baseline.

2. Подготовьте train пары с проверенными hard negatives: похожая, но неверная редакция/единица/условие. Эксперт независимо проверяет, что negative действительно нерелевантен. Ни test, ни его relevance не используются для mining.

3. Для автономного пути выполните реальное обучение reranker из скрипта, затем замените демонстрационные пары собственным разрешённым train. Разделите группы запросов/документов и сохраните provenance, seed, LR/steps и model snapshot.

4. Запустите serving/rerank с RERANKER_PATH на адаптированный каталог. На одном финальном наборе и одном кандидатном пуле сравните pretrained/adapted по Recall@k, MRR/nDCG, latency и срезам.

5. Покажите learning curve/ограничения объёма и экспертную проверку результатов. Если ошибка не в выбранном компоненте или улучшения нет, обоснуйте отказ от адаптированного варианта.

## Команды для воспроизводимого старта

```powershell
docker compose stop inference
docker run --rm --gpus all --network none --mount "type=bind,source=${PWD},target=/kit" --mount "type=bind,source=${PWD}/models,target=/models,readonly" course-gpu:2026-11 python scripts/train_reranker.py --steps 12
# Для оценки измените RERANKER_PATH в своей Compose-копии и пересоздайте inference.
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Negative оказался релевантным; relevant отсутствует в пуле; train/test разделены строками одного шаблона; tuning на финальном test.

## Самопроверка и критерии приёмки

выбор обоснован диагностикой; использованы hard negatives и независимая человеческая валидация; измерены Recall@k, MRR/nDCG и latency; достаточность выборки обсуждена, фиксированные 150–200 пар не считаются универсальным доказательством.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

диагностика выбора, размеченные пары/negatives, обученная модель/run.json, pretrained/adapted таблица и независимая экспертная проверка.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Четыре пары скрипта проверяют механику и не заявляют качество. Для embedding-ветки нужен собственный contrastive training с тем же протоколом; переименование reranker не заменяет выбор по диагнозу.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки
