# П8.4. Сравнение подходов и регрессии

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 4 ак. ч. (180 минут). Работа обязательна на базовом уровне. Подготовка — 25 мин; реализация/эксперимент — 80; негативные случаи — 45; анализ и оформление — 30. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Сравнить prompting, RAG и fine-tuning честно и проверить регрессии через финальный serving.

## Перед началом

П8.2–П8.3, baseline П1/П4; теория 8, раздел 8. Финальный набор хранится независимо до фиксации вариантов.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p8-4-approach-comparison-and-regressions/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Одна задача статуса/ответа с источниками, base/adapter, корпус и заранее закреплённые финальные группы. Условия доступности контекста должны быть явно одинаковыми для сравниваемых вариантов.

## Порядок самостоятельного выполнения

1. Задайте таблицу вариантов: base prompting, base+RAG, adapter с тем же входом и при необходимости adapter+RAG. Укажите, какие факторы меняются; статусную классификацию нельзя сравнивать с ответом на другую задачу.

2. Зафиксируйте метрики/пороги до открытия test: целевое качество/схема/unknown, общие задачи, русский язык, следование инструкциям, безопасность, latency/VRAM и стоимость. Выделите критичные инварианты.

3. На одном отложенном наборе соберите построчные результаты всех вариантов через API. Прогоните base FP16/NF4 и adapter NF4, которые реально будут демонстрироваться. Не заявляйте качество merge/GGUF, если конверсия не проверена.

4. Разберите целевые улучшения и регрессии/забывание: отказ без источника, injection, общие инструкции, цифры/единицы, избыточные ответы. Сохраните отрицательные результаты и неопределённость по независимым группам.

5. Подготовьте решение: оставить base, RAG, adapter либо no-go. Включите цену разметки/экспертов/serving. Повторная настройка после test требует новой версии и свежего независимого набора для нового утверждения о переносе.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/benchmark.py --prompt v2
# Сохраняйте результаты по каждому варианту, иначе benchmark-v2.json перезапишется.
docker compose run --rm lab python scripts/rag.py --mode lexical --answers
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Adapter снизил loss, но чаще отвечает без основания; RAG индексировал test-ответ; сравнение разных задач/контекста; лучший checkpoint выбран по test.

## Самопроверка и критерии приёмки

измерены целевое качество, общие возможности, следование инструкциям, безопасность, регрессии/забывание и качество после serving-квантования; вывод может быть в пользу отказа от fine-tuning; результаты воспроизводимы без использования теста для настройки.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

матрица вариантов, неизменный test manifest, API-ответы, срезы target/general/safety/quantization, цена и аргументированное решение.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Сравнивайте не только schema correctness. Для RAG-ветки эталонный корпус разрешён, но test-вопросы/ответы/labels не индексируются. Открытые комплектные наборы — regression/demo.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p8-4-approach-comparison-and-regressions.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
