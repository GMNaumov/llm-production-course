# П7.2. Генерация проверяемого изменения

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Получить небольшой C#-патч и провести его через сборку, поведенческие проверки, анализ и review.

## Перед началом

П7.1; теория 7, разделы 3–4. Не открывайте эталон патча до собственной попытки.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p7-2-verifiable-code-change/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Задача: добавить проверки отрицательных ordered/completed и completed>ordered, сохранив decimal, сигнатуру и ArgumentOutOfRangeException с ParamName.

## Порядок самостоятельного выполнения

1. Составьте промпт с контрактом, target net8.0, запретом новых пакетов/миграций/auth изменений и бюджетом попыток. Получите patch от разрешённой модели, сохраните prompt и сырой diff.

2. До применения прочитайте diff: нет ли удаления тестов, смены типов, новых зависимостей или выдуманных API. Примените только в work-копии, не в исходном эталоне.

3. Выполните build и исходные проверки. Добавьте независимые поведенческие случаи: ordered<0, completed<0, completed>ordered, равенство, ноль и дробное количество. Убедитесь, что новые проверки обнаруживают исходный код.

4. Запустите согласованные анализаторы и проверьте публичную сигнатуру/контракты исключений. Не считайте отформатированный код основанием принять изменение.

5. Проведите ручное review с коллегой: требование, смысл, совместимость, безопасность. После собственной попытки откройте reference/QuantityRules.cs и сравните причины различий. В отчёте разделите исходный ответ модели и ручную доработку.

## Команды для воспроизводимого старта

```powershell
# В собственной копии: dotnet build -c Release; затем ваши поведенческие проверки.
# Для сверки эталона: dotnet run --project reference/Reference.csproj -c Release
# Запуск в Docker описан в README комплекта.
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Модель меняет decimal на double; удаляет CancellationToken в другой задаче; создаёт новый exception contract; тест повторяет реализацию и не ловит исходную ошибку.

## Самопроверка и критерии приёмки

проект компилируется; существующие и релевантные новые тесты проходят; нет новых критичных замечаний согласованного статического анализа; архитектурные ограничения сохранены; изменение прошло человеческое review и не применялось в production.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Как проверить, что новый регрессионный тест действительно полезен?

## Что представить для сверки

prompt/patch, исходный и изменённый build/checks/analyzers, review.md и журнал ручных изменений.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Зелёные тесты той же модели могут разделять неверную гипотезу. Ожидания берите из требования; покажите, что граница падает на baseline и проходит на патче.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p7-2-verifiable-code-change.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
