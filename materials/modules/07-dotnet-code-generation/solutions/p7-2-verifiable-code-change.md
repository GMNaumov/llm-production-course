# Эталон П7.2. Генерация проверяемого изменения

[Задание](../practice/p7-2-verifiable-code-change.md) · [Теория](../self-study.md) · [Правила сверки](../../../practice-kit/README.md)

Эталон показывает один корректный вариант и границы вывода. Сначала выполните собственную попытку; затем сравните поведение, методику и причины расхождений. Код и таблицы не оценивают работу участника автоматически.

## Разбор решения

Эталон в dotnet/reference/QuantityRules.cs проверяет ordered<0, затем completed<0 или completed>ordered и возвращает ordered−completed. Имя параметра исключения — ordered либо completed.

Семь инженерных проверок эталона включают штатное, ноль, полное завершение, дробный остаток и три отказа. Допустима другая реализация с тем же наблюдаемым контрактом и пройденным человеческим review. Она не применяется в production.

## Как сравнить собственный результат

1. Сопоставьте артефакты с каждым критерием [программы](../../../../curriculum.md) и задания. Укажите доказательство.
2. Разберите хотя бы одно расхождение: методика, набор/версия, ошибка кода, неопределённость или ожидание. Не подгоняйте финальный test под эталон.
3. Подтвердите негативные случаи: Модель меняет decimal на double; удаляет CancellationToken в другой задаче; создаёт новый exception contract; тест повторяет реализацию и не ловит исходную ошибку.
4. Зафиксируйте ограничения: Зелёные тесты той же модели могут разделять неверную гипотезу. Ожидания берите из требования; покажите, что граница падает на baseline и проходит на патче.
5. Передайте отчёт на ручное review. При одиночном прохождении независимая проверка остаётся ожидающей коллегу/преподавателя; собственная сверка её не заменяет.

Как проверить, что новый регрессионный тест действительно полезен?
