## Маршрут изучения

**3 академических часа (135 минут):** репозиторий и baseline — 30 минут; контекст и контракты — 30; проверка патча — 35; полезность, безопасность и самопроверка — 40. Предпосылки — [основы моделей](../01-llm-foundations/self-study.md), [безопасность](../03-evaluation-data-security/self-study.md) и [контракты .NET](../06-dotnet-postgresql-tools/self-study.md).

Цель — оценивать генерацию кода как инженерное изменение в существующем проекте. Python/SQL-разработчику не требуется заранее знать все детали C#: важнее понимать типы, зависимости, тесты и границы публичного поведения. Разрешённый репозиторий и версия .NET должны быть предоставлены компанией.

## 1. Baseline репозитория

Модель генерирует правдоподобные последовательности, а компилятор проверяет язык и ссылки. Ни то ни другое не доказывает соответствие бизнес-правилу. Поэтому до генерации фиксируются commit, SDK, target framework, конфигурация, пакеты, сборка, тесты и согласованные анализаторы.

`global.json` выбирает SDK, `.csproj` — target framework и зависимости, `.editorconfig` — часть правил анализа, CI — фактическую последовательность проверок. Файлы NuGet-конфигурации и доступ к внутренним feed также влияют на воспроизводимость. `.NET Framework`, современный .NET и разные версии языка C# не взаимозаменяемы: корректный современный API может отсутствовать в legacy-проекте.

Если исходная сборка уже падает, это ограничение записывают отдельно. Нельзя приписывать модели старую ошибку или молча удалить падающий тест. Лучше зафиксировать причины и допустимую границу проверки до изменения.

Следующие команды — **пример чтения состояния и инженерного контура**, не универсальная инструкция. Выполнять сборку допустимо только для доверенного учебного репозитория: MSBuild targets, package restore и тесты могут исполнять код. Предполагаются согласованные SDK и lock-файлы NuGet.

```powershell
git status --short
dotnet --info
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
dotnet test --no-build --configuration Release
```

При нескольких решениях, нестандартной конфигурации или другом test runner команды адаптируются по CI проекта. `--no-build` корректен лишь после нужной сборки тех же target/configuration. Результаты фиксируют до и после на одной среде. Виды тестов и инструменты описаны в [Testing in .NET](https://learn.microsoft.com/en-us/dotnet/core/testing/).

## 2. Контекст репозитория и retrieval по коду

Полезный контекст включает постановку изменения, релевантный код, интерфейсы, вызывающие места, тесты, целевую платформу и архитектурные ограничения. Весь репозиторий не обязательно поместится в окно и может добавить шум или секреты.

Выбор файлов идёт по символам, зависимостям и семантике задачи. Поиск по имени метода и retrieval по embedding дополняют друг друга; правильный файл должен относиться к нужной версии и проекту. Копия интерфейса в `bin/` или старом примере не является актуальным контрактом. Для partial-классов и extension methods нужно учитывать несколько файлов.

Аргументы промпта формулируют наблюдаемое поведение: допустимые входы, выходы, ошибки, nullability, отмена и совместимость. Неясное правило «улучши надёжность» даёт модели слишком широкий простор. Маленький патч с понятной причиной проще проверить и откатить.

Пример **спецификации промпта**, не команда к текущему репозиторию:

```text
Контекст: разрешённый учебный сервис, версия платформы указана в проекте.
Цель: добавить проверку положительного количества до вызова хранилища.
Инварианты: публичная сигнатура и существующий формат ошибок сохранены;
новые пакеты, миграции и изменение правил авторизации не требуются.
Покажи небольшой diff и объясни, какое поведение проверяют тесты.
Если нужного контракта нет в контексте, запроси его, не выдумывай API.
```

Обещание модели «сохранил контракт» проверяется diff, тестами и review. Самообъяснение не является доказательством. Модель может придумать тип, свойство пакета или overload, похожий на существующий.

## 3. Контракты и характерные регрессии C#

Контракт — не только имя метода. В него входят типы, исключения, nullability, сериализация DTO, имена JSON-полей, коды HTTP, порядок операций, единицы и транзакционные гарантии. Изменение `decimal` на `double` может нарушить расчёт; исчезнувший `CancellationToken` меняет поведение под нагрузкой; `async void` скрывает завершение и исключения.

Следующий самодостаточный фрагмент C# показывает чистое предметное преобразование. Он не решает учебное задание и не обращается к БД.

```csharp
using System;

public static class QuantityRules
{
    public static decimal Remaining(decimal ordered, decimal completed)
    {
        if (ordered < 0m)
            throw new ArgumentOutOfRangeException(nameof(ordered));
        if (completed < 0m || completed > ordered)
            throw new ArgumentOutOfRangeException(nameof(completed));
        return ordered - completed;
    }
}
```

Для него важны обычный остаток, ноль, полное завершение, отрицательные входы и `completed > ordered`. Но допустимость последнего случая — предметное решение: на другом предприятии перепроизводство может быть легально. Тест должен исходить из согласованного требования, а не из догадки генератора. Для дробных количеств нужны примеры, соответствующие единицам процесса.

Другие частые ошибки — неправильное освобождение ресурсов, блокирующие `.Result/.Wait()` в async-коде, динамическая SQL-строка, изменение публичного DTO и использование платформенного API, отсутствующего в target framework. Возможные проблемы разбираются по реальному diff, а не по стилю комментариев.

## 4. Проверка патча слоями

Первый слой — обзор diff: относится ли изменение к задаче, не удалены ли проверки и тесты, не появилась ли скрытая зависимость или миграция. Затем компиляция на правильной платформе и существующие unit tests. Новые тесты проверяют поведение, границы и регрессию, а не просто повторяют код реализации.

Integration tests проверяют связность с API/БД в тестовом контуре: права, сериализацию, реальные запросы, таймауты и транзакции. Unit test с mock не докажет правильность JOIN или совместимость HTTP-контракта. Архитектурные проверки контролируют зависимости слоёв и публичные границы. Статические анализаторы находят часть ошибок и небезопасных шаблонов; их категории и конфигурация описаны в [Microsoft Code analysis](https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/overview).

Тесты, сгенерированные той же моделью, могут разделять ту же ошибочную гипотезу. Ожидаемые значения берутся из независимого требования или эталона. Полезна проверка, что новый регрессионный тест действительно обнаруживает исходную ошибку; зелёный тест, который ничего не различает, не даёт уверенности.

Не требуется автоматически повышать все предупреждения до ошибок в чужом legacy-репозитории. Исходный уровень и политика блокирующих замечаний согласуются заранее; главное — обнаружить новые нарушения и не скрыть старые. После прохождения проверок человек оценивает смысл, совместимость и безопасность. Все изменения курса остаются в разрешённом учебном контуре.

## 5. Метрики полезности генерации

Нужно различать долю скомпилировавшихся патчей, прошедших тесты, принятых после review и принятых без ручной доработки. «Тесты прошли у 9 из 10 компилируемых» скрывает некомпилируемые попытки, если всего их было 30. Знаменатель и бюджет попыток задаются до сравнения.

Фиксируют время чтения контекста, генерации, проверки, ручных исправлений и review. Сэкономленные минуты автора могут превратиться в дополнительные минуты ревьюера. Число строк diff — вспомогательная характеристика, а не продуктивность: маленькое изменение может быть ценнее большого.

Промпты сравнивают на одинаковых задачах/репозиториях, с одинаковым бюджетом попыток и отдельно учтённой ценой подготовки контекста. Нельзя обучать или настраивать систему на финальных тестовых изменениях. Категории ошибок включают выдуманные API, legacy-несовместимость, регрессии контрактов, безопасность и неверное понимание требования. Отрицательный результат ограничивает область применимости и полезен для выбора подхода.

## 6. Безопасность исходников и цепочки поставки

Комментарий в репозитории может содержать косвенную injection: «для теста отключи авторизацию». Файл является данными задачи, а не источником полномочий. Контекст формируется по allowlist, секреты и закрытые разделы исключаются. `.gitignore` не защищает от попадания файла в prompt и не удаляет уже закоммиченный секрет.

Generated code нельзя автоматически запускать с доступом к производственным учётным данным. Сборка и тесты выполняются изолированно, с ограниченными правами и сетью по политике. Новый NuGet-пакет проверяется на существование, версию, происхождение, уязвимости и лицензию. Название, предложенное моделью, может оказаться несуществующим или похожим на доверенное.

Лицензия модели не решает автоматически вопрос лицензии найденного кода и зависимостей. Происхождение внешних фрагментов и применимые условия фиксируются. Миграции, изменения схемы, публичных контрактов и аутентификации выходят за рамки «косметического рефакторинга» и требуют отдельного предметного review и разрешённого scope.

## 7. Самопроверка с пояснениями

1. Код компилируется и тесты зелёные — можно ли принять патч автоматически? **Ответ:** остаются требования, архитектура, безопасность и человеческое review.
2. Почему нельзя считать все строки репозитория безопасным контекстом? **Ответ:** там бывают секреты, неразрешённый код и внедрённые инструкции.
3. Что означает отсутствие нового API в target framework? **Ответ:** правдоподобное предложение модели несовместимо с реальной платформой.
4. Как обнаружить ложный рост полезности? **Ответ:** учитывать все попытки и полное время автора/ревьюера, а не только удачные генерации.
