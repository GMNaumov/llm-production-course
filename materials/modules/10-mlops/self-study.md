Цель — объяснить, как эксперимент превращается в управляемый выпуск: с владельцами, доступом, измерениями, ограничением нагрузки и способом восстановления. Контейнерный прототип не становится production-ready автоматически.

## 1. Граница LLM-сервиса

Типовой путь: `клиент → API-шлюз → прикладной workflow → retrieval/tools → inference`. Шлюз централизует аутентификацию, разрешённые маршруты, rate limits, quotas и аудит. Прикладной сервис сохраняет предметные проверки, а каждый инструмент — собственную авторизацию. Наличие шлюза не отменяет защиту внутренних сервисов от прямого обхода.

FastAPI может реализовать прикладную обёртку и часть политик, но сам выбор фреймворка не обеспечивает безопасность. Для входа задают типы, размер, длину контекста, бюджет ответа, таймаут и допустимый маршрут модели. Клиент не должен произвольно менять system prompt, model path или адрес инструмента, если это не предусмотрено политикой.

Rate limit ограничивает частоту запросов, quota — суммарный ресурс за период, concurrency limit — одновременно выполняемую работу. Один запрос на 200 страниц может потребить больше, чем сто коротких вопросов. Для LLM полезно учитывать токены, страницы и занятые GPU-секунды, а не только HTTP QPS. Учёт ресурса делается по серверным данным, а не по обещанию клиента.

Маршрутизация выбирает согласованный набор «модель + prompt + данные + инструменты», а не случайно самую доступную модель. Резервная модель может иметь другую схему, лицензию и качество. Автоматическая отправка промышленного запроса в облако при локальном отказе запрещена границами курса.

## 2. Что наблюдать без утечки

Метрики показывают агрегаты, трассы — путь запроса через компоненты, журналы — события. Полезны request/trace ID, release ID, route, outcome, версия политики, длительности этапов, число входных/выходных токенов и категории ошибок. Метрики качества поступают также из экспертной выборки, HITL и согласованных проверок, а не только из исправности HTTP.

Не следует автоматически сохранять prompt, содержимое документов, исходный код, токены доступа и SQL-результаты. Разрешённый список полей проще проверить, чем бесконечный список запрещённых. Очистка должна происходить до экспорта, включая исключения и debug-режим. [OpenTelemetry](https://opentelemetry.io/docs/security/handling-sensitive-data/) описывает минимизацию и обработку чувствительных данных.

Python, стандартная библиотека; пример allowlist-события на синтетике:

```python
import json

def public_event(*, request_id, release_id, outcome, latency_ms):
    if outcome not in {"ok", "refused", "timeout", "dependency_error"}:
        outcome = "dependency_error"
    return {
        "request_id": request_id,
        "release_id": release_id,
        "outcome": outcome,
        "latency_ms": round(latency_ms, 1),
    }

print(json.dumps(public_event(
    request_id="synthetic-17", release_id="training-r3",
    outcome="refused", latency_ms=125.46
)))
```

ID создаётся доверенным компонентом, а не берётся из произвольного текста запроса. В реальном сервисе проверяются конечность и единицы чисел. Даже метаданные могут быть чувствительными; для логов нужны доступ, retention, удаление и аудит. Не включайте высококардинальные request IDs или тексты в labels метрик: это увеличивает стоимость и риск раскрытия.

## 3. Производительность: очередь, prefill и decode

End-to-end latency включает очередь, retrieval/OCR/tools, prefill модели, последовательный decode и проверки. Time to first token (TTFT) не равен времени до завершённого ответа. Tokens per second нужно разделять на поток одного пользователя и суммарный throughput сервера. Ускорение за счёт более коротких, но неполных ответов не является улучшением качества сервиса.

Batching повышает эффективность GPU, но может увеличить ожидание; KV cache и максимальный контекст ограничивают concurrency. В тесте сохраняют распределение входных/выходных длин, долю длинных документов, прогрев, кэширование и модель подачи нагрузки. Закрытая модель, где следующий запрос ждёт завершения предыдущего, может скрывать перегрузку реального входящего потока.

Для устойчивой системы закон Литтла даёт `L ≈ λW`: среднее число запросов в системе равно интенсивности поступления, умноженной на среднее время пребывания. При 0,5 запроса/с и 8 с это около 4 запросов в работе и очереди. Это средние при устойчивом режиме, не формула для P95 и не гарантия достаточности четырёх слотов.

По мере приближения к пределу обслуживания очередь и хвостовая latency быстро растут. Наблюдают P50/P95, ошибки, throughput, глубину/возраст очереди, concurrency, CPU/RAM/GPU/VRAM и полезный результат. Метод расчёта процентилей и число наблюдений указываются; нагрузочные проверки не должны незаметно менять набор задач.

RTX 3060 — учебная платформа. Production sizing определяется реальными длинами, числом пользователей, нагрузкой OCR/VLM, резервированием, охлаждением, SLA и требованиями к сопровождению. Число «запросов в секунду» без профиля нагрузки почти бесполезно.

## 4. Backpressure, таймауты и деградация

Очередь ограничивают по длине и времени ожидания. При перегрузке запрос отклоняется контролируемо, а не хранится бесконечно. Admission control проверяет доступный бюджет до тяжёлой работы; отмена клиента должна по возможности освобождать ресурсы downstream. Ограничения apply одновременно к пользовательским запросам и внутренним вызовам агента.

Retries без бюджета увеличивают нагрузку на уже отказавшую зависимость. Нужны общий deadline, ограниченное число попыток, backoff/jitter и соблюдение идемпотентности. Circuit breaker временно прекращает обращения к явно недоступной зависимости, но не должен превращать отказ в фиктивный успех. Принципы перегрузки рассматривает [Google SRE: Handling Overload](https://sre.google/sre-book/handling-overload/).

Liveness проверяет, что процесс способен работать; readiness — что экземпляр может принять нужный тип запроса. Перезапуск исправного процесса при кратком отказе внешней БД способен усилить инцидент. Состояние GPU-модели и индекс/конфигурация входят в готовность конкретного маршрута.

Деградация — заранее проверенное сокращение возможностей: выдать обычные результаты поиска без генерации, направить документ на ручной разбор, отложить некритичную обработку. Она сохраняет ACL, маркирует режим и не угадывает критичные поля. Для write неизвестный исход разбирается сверкой, как в [модуле 6](../06-dotnet-postgresql-tools/self-study.md).

## 5. Выпуск как набор связанных версий

MLOps дополняет обычный CI/CD управлением данными, моделями и оценкой. Нужны функции учёта экспериментов, хранения артефактов, версионирования данных/индекса и допуска выпуска. Их можно реализовать согласованными инструментами: например, MLflow для экспериментов и реестра, Git для кода/конфигураций, локальное объектное хранилище для тяжёлых артефактов, OpenTelemetry для трасс. Это варианты распределения функций, а не обязательный список продуктов. Инструмент не устраняет необходимость owners, backup, прав и проверки восстановления.

Модель без prompt и корпуса не задаёт поведение. Манифест связывает код, образ, базу/адаптер, tokenizer/template, prompts, данные, индекс, tool schemas, политики и конфигурацию. Хэши ниже — **явные заполнители**, не настоящие контрольные суммы и не готовый release.

```yaml
release_id: training-r3
code_commit: "<git-commit>"
image: "<local-registry/image@sha256:digest>"
model:
  revision: "<approved-base-revision>"
  checksum: "<model-sha256>"
  adapter_checksum: null
tokenizer_template_checksum: "<sha256>"
prompt_checksum: "<sha256>"
corpus_snapshot: "<approved-corpus-version>"
index_snapshot: "<index-version>"
embedding_revision: "<embedding-revision>"
tool_schema_checksum: "<sha256>"
policy_version: "<policy-version>"
config_checksum: "<sha256>"
evaluation_report: "<approved-report-id>"
```

Манифест не содержит секретов; он указывает безопасные ссылки/версии политик получения. Офлайн-пакет включает все необходимые артефакты, зависимости, лицензии и checksums. Выгрузка образа не включает volumes автоматически; модель и индекс обеспечиваются отдельно.

Rollout сначала проверяет комплект на чистой среде, затем ограниченно переключает разрешённую нагрузку. Gate проверяет качество и безопасность до допуска; наблюдение после переключения выявляет неизвестные отказы. Canary или blue/green возможны при наличии ресурсов; Kubernetes не обязателен. На одной учебной GPU одновременное удержание двух моделей может быть невозможно, что учитывается в процедуре.

## 6. Rollback, backup и восстановление

Rollback возвращает согласованный комплект версий, а не только Docker image. Новый код может требовать другую схему/индекс; обратная совместимость проверяется заранее. Откат приложения не отменяет уже выполненные внешние операции и не восстанавливает автоматически старые права. Для опасных миграций нужен отдельный план, а в курсе production-изменения исключены.

Backup имеет ценность только после проверки restore. Определяют допустимую потерю состояния (RPO) и время восстановления (RTO), сохраняют конфигурации, индекс/источники по политике и журнал удалений/отзывов. При восстановлении повторяются ACL, tombstones, ссылки и регрессии: старый backup не должен вернуть доступ к удалённому документу.

Владельцы распределяются по функциям: процесс и бизнес-критерии, данные/индекс, модель/оценка, API/интеграции, ИБ, инфраструктура и поддержка пользователей. Одно лицо может совмещать роли, но ответственность за инцидент, обновление источников и остановку должна быть явной. Runbook описывает наблюдаемый симптом, диагностику, допустимое восстановление и эскалацию.

## 7. Самопроверка с пояснениями

1. Почему средняя latency не показывает перегрузку? **Ответ:** очередь и длинный хвост могут расти при приемлемом среднем.
2. Можно ли автоматически переключить промышленный запрос в облако? **Ответ:** нет, это нарушит подтверждённую границу данных.
3. Почему rollback образа не равен rollback выпуска? **Ответ:** изменяются также модель, prompt, индекс, схемы и конфигурация.
4. Что доказывает успешный backup без restore? **Ответ:** только создание копии, но не возможность восстановления.
