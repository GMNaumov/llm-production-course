# П10.2. Нагрузка и отказ зависимостей

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Измерить хвост latency и поведение перегрузки/отказов под воспроизводимой нагрузкой.

## Перед началом

П10.1; теория 10, разделы 3–4. Данные и профиль запросов фиксированы; учебный GPU не считается production sizing.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p10-2-load-and-dependency-failures/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`scripts/load.py`, /live и /ready, nvidia-smi/docker stats; локальные модели/БД/API. Короткий search-прогон нужен для настройки методики, не как LLM throughput.

## Порядок самостоятельного выполнения

1. Задайте число запросов, длины входа/выхода, прогрев, cache, число клиентов и модель нагрузки. Начните с 1, затем 2/4/8 клиентов. Закрытая модель load.py не учитывает ожидание генератора до слота клиента — отметьте это.

2. Снимайте завершения/успехи в секунду, P50/P95 всех запросов и успешных отдельно, 429/503/timeouts, CPU/RAM и GPU/VRAM. Не улучшайте P95 удалением ошибок из отчёта.

3. Проверьте ограниченные concurrency/очередь/ожидание, общий deadline и освобождение слотов. Для открытого потока по расписанию отдельно измерьте backlog/время ожидания; 20 коротких запросов не доказывают устойчивость.

4. Остановите inference, db и api по одному в тестовом стенде. Вызовите зависимый маршрут: RAG, SQL, API-client соответственно. /live процесса не должен зависеть от краткого отказа БД; readiness нужного маршрута — должен.

5. Восстановите зависимости и повторите штатные запросы. Укажите границы проверенной нагрузки, RTO восстановления и требования к production GPU/резерву/эксплуатации без экстраполяции по одному ПК.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/load.py --clients 1 --requests 20 --route rag
docker compose run --rm lab python scripts/load.py --clients 4 --requests 20 --route rag
docker compose stop inference
docker compose run --rm lab python scripts/load.py --clients 2 --requests 10 --route rag
docker compose --profile gpu up -d inference
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

429 при перегрузке, модель/БД/API недоступны, длинный запрос держит слот, retries усиливают отказ. Деградация сохраняет права и маркируется.

## Самопроверка и критерии приёмки

измерены throughput, P50/P95 latency, ошибки, concurrency и GPU/VRAM; очередь и backpressure предотвращают неконтролируемое исчерпание ресурсов; health checks и деградация работают; указаны ограничения RTX 3060 и требования к production-среде.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Почему высокий throughput с быстрыми 429 не означает полезную пропускную способность?

## Что представить для сверки

профиль нагрузки, raw rows, сводные P50/P95/throughput/errors, GPU/stats, fault matrix и runbook восстановления.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Если из-за rate limit все запросы 429, это измерение политики, а не скорости модели. Согласованно измените лимит в своей тестовой конфигурации до следующего прогона и сохраните версию.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
