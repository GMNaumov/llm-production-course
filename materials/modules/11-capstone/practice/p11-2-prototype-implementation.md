# П11.2. Сборка прототипа

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 5 ак. ч. (225 минут). Работа обязательна на базовом уровне. Подготовка — 35 мин; реализация/эксперимент — 100; негативные случаи — 55; анализ и оформление — 35. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Собрать один воспроизводимый сценарий с правами, аудитом, отказами и HITL.

## Перед началом

П11.1; теория 11, раздел 3. Все необходимые компоненты созданы в предыдущих работах, образы/модели подготовлены.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p11-2-prototype-implementation/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Собственный Compose-репозиторий; reference комплект как пример поведения, а не замена самостоятельной интеграции.

## Порядок самостоятельного выполнения

1. Соберите в отдельной work-копии только компоненты выбранного сценария. README должен задавать prerequisites, offline artifacts, secret provisioning, запуск, readiness, штатный запрос и ожидаемые свойства.

2. Проследите identity→ACL→retrieval/tool→generation→validation→HITL→audit. Для документов покажите очередь/источник; для кода — patch/review; для действий — preview и отдельное явное человеческое подтверждение.

3. Выполните штатный случай и негативные: нет данных, чужой объект, injection, timeout зависимости, неверная schema и replay при наличии действий. Проверяйте фактические эффекты и состав контекста.

4. Передайте комплект другой команде или коллеге с новым context/ПК и новыми учебными секретами. Автор наблюдает, но не исправляет скрыто. Любая необходимая подсказка попадает в README, затем запуск повторяется.

5. Сохраните manifest, логи по allowlist, результаты, известные ограничения и индивидуальные вклады. Продемонстрируйте, что production endpoints/credentials не требуются и не встроены в конфигурацию.

## Команды для воспроизводимого старта

```powershell
docker compose config --quiet
docker compose run --rm secrets-init
docker compose --profile gpu up -d --wait inference gateway
docker compose run --rm lab python scripts/load.py --route search --clients 1 --requests 5
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Демо работает только с cache автора; секрет в Compose; ACL фильтруется после генерации; dependency error возвращает выдуманный ответ; confirm делает модель.

## Самопроверка и критерии приёмки

другая команда запускает проект на чистой среде; штатный и негативные сценарии воспроизводятся; права, аудит, HITL, отказ зависимостей и отсутствие секретов проверены; production-изменения исключены.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Что считать скрытой зависимостью, если коллеге для запуска понадобился ваш домашний каталог?

## Что представить для сверки

репозиторий/README/manifest, законченный сценарий, протокол чистого запуска другой командой, негативные следы и вклад участников.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Самостоятельное прохождение возможно до передачи на независимое review. Если второй команды нет, нужен коллега/преподаватель; собственный повтор не записывают как независимый.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p11-2-prototype-implementation.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
