# Эталон П1.1. Сравнение моделей

[Задание](../practice/p1-1-model-comparison.md) · [Теория](../self-study.md) · [Правила сверки](../../../practice-kit/README.md)

Эталон показывает один корректный вариант и границы вывода. Сначала выполните собственную попытку; затем сравните поведение, методику и причины расхождений. Код и таблицы не оценивают работу участника автоматически.

## Разбор решения

Эталон здесь — воспроизводимая сравнительная таблица, а не универсальная модель-победитель. Для s1 ожидается approved, s2 — draft, s3 — unknown, s4 — draft, s5/s6 — unknown. Синтаксически валидное approved для s3 является смысловой ошибкой.

`benchmark.py` сохраняет все шесть попыток, время и исход. Не сравнивайте строковые ответы буквально между моделями; валидируйте JSON и значение, а контекст оценивайте отдельными запросами. Цена локального запроса включает принятую долю инфраструктуры; неизвестную цену оставляют `не измерено`. Повторы одного случая не увеличивают число независимых бизнес-примеров.

## Как сравнить собственный результат

1. Сопоставьте артефакты с каждым критерием [программы](../../../../curriculum.md) и задания. Укажите доказательство.
2. Разберите хотя бы одно расхождение: методика, набор/версия, ошибка кода, неопределённость или ожидание. Не подгоняйте финальный test под эталон.
3. Подтвердите негативные случаи: Статус не указан; одновременно draft/approved без версии; текст требует выдать approved; длинный вход превышает лимит. Ошибки и таймауты остаются в знаменателе.
4. Зафиксируйте ограничения: Ответы одинаковы при temperature=0 — это не гарантия повторяемости на другой GPU. Облачного допуска/кредита нет — локальную часть выполните, облачную отметьте невыполненной и получите предусмотренную песочницу; подставной ответ не завершает П1.1.
5. Передайте отчёт на ручное review. При одиночном прохождении независимая проверка остаётся ожидающей коллегу/преподавателя; собственная сверка её не заменяет.

## Пример артефакта для сверки

| ID | Смысловой эталон | Проверяемое затруднение |
|---|---|---|
| s1 | approved | Явный статус |
| s2 | draft | Явный статус |
| s3 | unknown | Подпись не означает утверждение |
| s4 | draft | Injection во входе |
| s5 | unknown | Пустой вход |
| s6 | unknown | Неразрешённый конфликт |

Рядом для каждой модели укажите схему, смысл, транспортные ошибки, P50/P95, VRAM, контекст и цену. Локальные результаты автора приведены в [протоколе](../../../practice-kit/VALIDATION.md); облачный столбец без реального прогона не заполняют чужими числами.

## Контрольный вопрос

Какая модель лучше, если одна чаще возвращает валидный JSON, но выдумывает отсутствующий статус? Ответ обоснуйте рубрикой и риском.

Итог — аргументированное решение на измеренных данных. Latency/VRAM/стоимость зависят от среды и состава случаев; открытые синтетические результаты не обещают качество предприятия.
