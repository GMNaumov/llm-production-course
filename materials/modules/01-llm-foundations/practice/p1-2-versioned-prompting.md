# П1.2. Версионируемый промптинг

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 2 ак. ч. (90 минут). Работа обязательна на базовом уровне. Подготовка — 15 мин; реализация/эксперимент — 40; негативные случаи — 25; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Получить измеримое сравнение двух версий промпта и безопасной обработки отсутствующих данных.

## Перед началом

Результаты П1.1; теория 1, раздел 5. Один зафиксированный endpoint, модель и параметры.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p1-2-versioned-prompting/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Открытый `status-dev.json`; исходные v1/v2 в `scripts/benchmark.py`. Финальные новые группы карточек передаёт другой участник после фиксации промпта.

## Порядок самостоятельного выполнения

1. Создайте `work/p1-2/protocol.md`: требуемая схема, правило unknown, единица сравнения, бюджет одной попытки и метрики. Сохраните текст v1, модель/template, лимит ответа и checksum dev.

2. Выполните v1. На dev разберите ошибки по категориям: парсинг, лишние поля, неверный статус, избыточный unknown, следование injection. Напишите собственный v2, меняя по одному существенному условию.

3. Включите few-shot только из разрешённого train/dev и отрицательный пример без статуса. Разберите, поддерживает ли endpoint constrained output. Учебный сервер проверяет ответ после генерации; не объявляйте это серверной JSON grammar.

4. Закрепите v2 в commit и протоколе до получения финальных карточек. Выполните v1/v2 на одних финальных случаях без дальнейшей настройки. Уже просмотренный финальный набор после исправления становится regression.

5. Посчитайте корректность по всем случаям, schema validity, доли корректных и избыточных unknown. Покажите парные изменения и отрицательные результаты. Порог приёмки согласуйте по риску до финального прогона.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/benchmark.py --prompt v1
# Сохраните work/benchmark-v1.json.
docker compose run --rm lab python scripts/benchmark.py --prompt v2
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Лишний JSON-ключ, строка вместо объекта, обрезанный ответ, противоречивый статус. Для невалидной структуры — контролируемая ошибка/повтор в пределах бюджета, затем unknown/ручная проверка.

## Самопроверка и критерии приёмки

версии и параметры зафиксированы; финальная проверка выполнена на отложенном наборе; измерены корректность, соблюдение схемы и корректность отказа; негативные результаты включены в отчёт.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Почему более высокий schema validity ещё не доказывает улучшения решения задачи?

## Что представить для сверки

v1/v2 с историей изменений, протокол до test, парная таблица ответов, схема и отчёт с классификацией отказов.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Few-shot не должен содержать финальную карточку или её перефразировку. Regex, вырезающий всё до первой скобки, может скрыть нарушение формата: фиксируйте сырой синтетический ответ и политику нормализации.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p1-2-versioned-prompting.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
