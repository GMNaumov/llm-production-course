# П1.1. Сравнение моделей

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Сравнить реальные ответы моделей на одинаковых русских примерах, отделив качество от работоспособности API.

## Перед началом

Теория модуля 1, разделы 1–5. Организатор заранее готовит GPU-профиль и два локальных снимка моделей по инструкции комплекта: использование готового endpoint в модуле 1 не требует предварительного прохождения модуля 2.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p1-1-model-comparison/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`data/status-dev.json` — шесть открытых синтетических случаев. Добавьте отраслевые обозначения, вопрос к началу/середине/концу контекста и отрицание. Получите у организатора отдельную финальную выборку и разрешённый облачный endpoint.

## Порядок самостоятельного выполнения

1. До прогона запишите модели/ревизии, лицензии из локальных model cards, методику оценки, предел входа/выхода, один прогревочный запрос и не менее двух независимых типов промышленных формулировок. Малый открытый набор используйте для отладки, не как доказательство промышленной точности.

2. Для первой локальной модели исполните benchmark. Сохраните `work/benchmark-v2.json` в отдельный каталог модели до следующего запуска. Повторите на второй локальной модели, меняя только модельный профиль и её корректный template. Третья локальная модель допустима, но не обязательна.

3. Измерьте P50/P95 полного ответа, входные/выходные токены, ошибки формата/транспорта и пик VRAM через nvidia-smi и серверные local_metrics. Проверяйте фактический контекст вопросами на разных позициях; 2048 в учебном сервере — лимит конфигурации, не заявленное окно модели.

4. В разрешённой облачной песочнице выполните тот же синтетический набор через benchmark с `--base`, `--model`, `--token-file`. Прочитайте инструкцию облачного запуска комплекта. Не отправляйте внутренние данные; тарифы и расходы фиксируйте по реальному биллингу, не по предположению.

5. Составьте парную таблицу по ID случая. Отдельно оцените схему, смысл статуса, unknown, отраслевые термины и контекст. Укажите число наблюдений, неопределённость, прогрев, ограничения и суммарные расходы в бюджете курса.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/benchmark.py --prompt v2
# Сохраните отчёт под именем модели перед повтором.
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Статус не указан; одновременно draft/approved без версии; текст требует выдать approved; длинный вход превышает лимит. Ошибки и таймауты остаются в знаменателе.

## Самопроверка и критерии приёмки

сравнены качество по заранее выбранной методике, P50/P95 latency, VRAM, фактический контекст, стоимость и лицензии; сохранены конфигурации; в облако переданы только разрешённые синтетические/обезличенные данные.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Какая модель лучше, если одна чаще возвращает валидный JSON, но выдумывает отсутствующий статус? Ответ обоснуйте рубрикой и риском.

## Что представить для сверки

`models.csv`, конфигурации и исходные ответы всех локальных/облачного прогонов, `comparison.md` с P50/P95, VRAM, контекстом, стоимостью и лицензиями.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Ответы одинаковы при temperature=0 — это не гарантия повторяемости на другой GPU. Облачного допуска/кредита нет — локальную часть выполните, облачную отметьте невыполненной и получите предусмотренную песочницу; подставной ответ не завершает П1.1.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p1-1-model-comparison.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
