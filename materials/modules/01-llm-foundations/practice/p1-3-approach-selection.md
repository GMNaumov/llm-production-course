# П1.3. Выбор подхода

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 1 ак. ч. (45 минут). Работа обязательна на базовом уровне. Подготовка — 5 мин; реализация/эксперимент — 20; негативные случаи — 10; анализ и оформление — 10. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Выбрать технологию по диагностированной причине ошибки и стоимости процесса.

## Перед началом

П0.1, П1.1–П1.2; теория 1, раздел 6.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p1-3-approach-selection/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

Три кандидата из карты процессов; при отсутствии корпоративных данных — поиск регламента, перенос полей спецификации, дефицит заказа.

## Порядок самостоятельного выполнения

1. Для каждого кандидата сформулируйте единицу задачи и наблюдаемую ошибку baseline. Разделите изменяемые факты, устойчивое поведение и точные вычисления.

2. Заполните матрицу вариантов: обычный код/правила/поиск, prompting, RAG, fine-tuning. Для каждого укажите данные, предполагаемую пользу, риск, сопровождение и эксперимент, который проверит предположение.

3. Выберите минимально достаточный подход и план сравнения с альтернативой. Для fine-tuning укажите, какая ошибка не устраняется промптом/контекстом; отсутствие такого основания означает отложить его для данного пилота.

4. Добавьте условия пересмотра: новый шаблон, рост ручной проверки, изменение ACL, объёма, стоимости или точности. Обменяйтесь матрицей с коллегой и устраните один необоснованный вывод.

## Негативные случаи

«Все знания в веса», «RAG исправит нечитаемый допуск», «LLM сама посчитает SQL». Найдите границу применимости каждого утверждения.

## Самопроверка и критерии приёмки

решение связано с типом ошибки, данными, риском и стоимостью; указаны условия, при которых выбранный подход следует пересмотреть.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

Какое наблюдение заставит заменить RAG улучшением OCR, а не новым промптом?

## Что представить для сверки

`approach-matrix.md`: три задачи × минимум четыре подхода, решение и триггеры пересмотра.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Обещания эффекта без эксперимента помечайте гипотезами. Наличие fine-tuning в программе не делает его обязательным для выбранного capstone.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.

## Эталон после собственной попытки

[Разобранное эталонное решение](../solutions/p1-3-approach-selection.md) позволяет сверить поведение и доказательства. Открытые данные/ответы не являются независимым test; финальные новые случаи готовит и хранит коллега/преподаватель. Корректный отрицательный эксперимент может быть принят.
