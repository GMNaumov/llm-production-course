Предпосылка — [модуль 1](../01-llm-foundations/self-study.md). Примеры объясняют устройство среды; конкретная [инструкция запуска](../../practice-kit/README.md) и задания доступны в практической части.

Результат чтения — способность отличить проблему драйвера от ошибки сервера, оценить нижнюю границу памяти и объяснить, почему файл модели и Docker-образ ещё не образуют воспроизводимый стенд.

## 1. Слои Windows → WSL2 → Docker → сервер → приложение

WSL2 предоставляет Linux-среду с собственным ядром. Docker Desktop с серверной частью на базе WSL2 управляет контейнерным движком; альтернативой является отдельно настроенный Docker Engine в WSL. Эти варианты требуют согласованной настройки: разные контексты Docker могут обращаться к разным наборам образов, томов и контейнеров. Вся группа должна использовать один согласованный вариант.

GPU доступен через Windows-драйвер с поддержкой WSL. Внутри контейнера находятся пользовательские CUDA-библиотеки и приложение; образ не заменяет драйвер хоста. NVIDIA отдельно предупреждает, что не следует устанавливать Linux-драйвер GPU внутри WSL: используйте правила [CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/index.html), а не обычную инструкцию для Linux. Проброс GPU средствами Docker Desktop в Linux-контейнеры под Windows описан в [документации Docker](https://docs.docker.com/desktop/features/gpu/).

Версия CUDA в выводе `nvidia-smi` отражает возможности драйвера, но не подтверждает наличие конкретного инструментария CUDA в контейнере. Проверка должна проходить по слоям: видимость GPU на хосте, доступ в WSL, доступ из контейнера, загрузка модели, ответ API и оценка ответа. Успешный `nvidia-smi` не доказывает, что инференс использует GPU: часть слоёв модели может остаться в RAM или на CPU.

Диагностические команды только читают состояние. Первый блок содержит команды **PowerShell для Windows**, второй — **bash в WSL**; выполнять их для чтения конспекта необязательно.

```powershell
wsl --status
wsl --list --verbose
docker context show
docker version
docker compose version
nvidia-smi
```

```bash
uname -r
nvidia-smi
docker context show
```

При ошибке важно зафиксировать, на каком уровне она возникла, её код и версии компонентов. Перед сохранением диагностического отчёта из него удаляют чувствительные пути и токены доступа. Перезапуск всех компонентов может временно скрыть причину и не позволяет установить, какое действие восстановило работу.

## 2. Из чего складывается VRAM

Для плотной модели нижняя оценка размера весов — `N × b / 8` байт, где N — число параметров, b — число бит на параметр. У 8B при 4 битах это 4 млрд байт, около 3,73 GiB. Реальный файл содержит масштабы квантования, метаданные и тензоры другой точности. В памяти дополнительно нужны KV-кэш, временные буферы, активации и память среды исполнения.

Для обычного KV-кэша decoder-модели полезна оценка:

`M_KV ≈ 2 × L × B × T × H_KV × D_head × bytes_per_element`.

L — число слоёв, B — число одновременно хранимых последовательностей, T — число токенов в каждой последовательности, H_KV — число голов ключей и значений, D_head — размерность одной головы внимания. Множитель 2 учитывает хранение и ключей, и значений. При использовании GQA число H_KV меньше числа голов запросов. Некоторые архитектуры и серверы используют иные схемы хранения, поэтому формула даёт ориентировочную оценку для диагностики, а не точный расход памяти.

Пример использует стандартную библиотеку Python и условную архитектуру:

```python
def gib(byte_count):
    return byte_count / (1024**3)


weight_bytes = 8_000_000_000 * 4 / 8
kv_bytes = 2 * 32 * 1 * 4096 * 8 * 128 * 2
print(round(gib(weight_bytes), 2))  # 3.73, только упакованные веса
print(round(gib(kv_bytes), 2))  # 0.50, только KV cache
```

При четырёх последовательностях такой длины KV-кэш займёт около 2 GiB; внутри одного процесса обычно используется одна общая копия весов. Несколько независимых серверных процессов могут продублировать веса. Допустимое число одновременных запросов определяют экспериментально для заданной длины контекста и ответа.

RTX 3060 12 ГБ ограничивает не только размер весов. Длинный контекст, VLM-изображения и параллелизм способны исчерпать память после успешной загрузки. Для обучения потребуются дополнительные активации, градиенты и состояния оптимизатора — оценка инференса неприменима напрямую. Перед QLoRA обязателен отдельный расчёт из [модуля 8](../08-fine-tuning/self-study.md).

## 3. Квантование и выбор сервера

Квантование представляет веса меньшим числом бит с дополнительными коэффициентами. Уменьшение памяти может сопровождаться потерей качества, особенно на редких терминах, точных числах и следовании схеме. Обозначение «4-bit» не задаёт единый алгоритм, разрядность всех тензоров и размер KV-кэша.

[GGUF](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) — формат хранения тензоров и метаданных, а не отдельная модель и не универсальный формат обучения. Обозначения квантования в GGUF нельзя считать эквивалентными NF4 из QLoRA. Поддержку архитектуры и токенизатора проверяют для конкретной ревизии сервера.

Для учебной среды подходят серверы на основе llama.cpp или другие совместимые движки. Выбор зависит от поддержки GPU, форматов моделей, вызова инструментов, схем ответа и офлайн-работы. Не выбирайте сервер только по заявленной пропускной способности на другой GPU. Обозначение «OpenAI-совместимый HTTP-интерфейс» указывает на сходство формата запросов и ответов, но не гарантирует совпадения всех возможностей и значений параметров. Сравнивать нужно конкретные поддерживаемые поля.

Качество квантованной модели сравнивают с доступным неквантованным или альтернативным baseline на неизменном наборе. Если исходная модель не помещается в доступную память учебного ПК, сравнение можно провести на согласованном on-prem резерве. Это ограничение эксперимента фиксируют, а не заменяют утверждением «квантование без потерь».

## 4. Контейнерный контракт и границы доступа

Образ фиксирует программное окружение; том хранит модели и состояние; сеть определяет доступность сервисов друг для друга. Тег (tag) может быть переназначен, а digest идентифицирует содержимое образа. Для выпуска нужны digest образа, контрольная сумма модели и ревизия токенизатора. Сам по себе digest не подтверждает надёжность источника образа.

Ниже приведён **иллюстративный Compose-фрагмент**, а не готовый стенд. Он предполагает заранее согласованный образ с сервером на порту 8080; переменная `INFERENCE_IMAGE` должна содержать ссылку на локально доступный образ с указанием digest. Команда запуска и способ проверки работоспособности определяются выбранным образом, поэтому в этом фрагменте не заданы.

```yaml
services:
  inference:
    image: ${INFERENCE_IMAGE:?set-approved-image-with-digest}
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - ./models:/models:ro
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

Настройка доступа к GPU через `reservations` описана в [Docker Compose GPU support](https://docs.docker.com/compose/how-tos/gpu-support/). Она запрашивает устройство, но не устанавливает лимит VRAM. Привязка порта к петлевому интерфейсу (loopback) разрешает подключение только через локальный интерфейс хоста; взаимодействие контейнеров, аутентификацию API и исходящий трафик нужно контролировать отдельно. Пользовательский интерфейс не должен открывать доступ к незащищённому серверу из сети предприятия.

Учебный стенд включает сервер инференса, Open WebUI и FastAPI-обёртку. Интерфейс нужен для интерактивной работы и наблюдения; обёртка ограничивает доступные операции, применяет политики и собирает измерения. Секреты модели не передаются. Проверка готовности (readiness) подтверждает, что модель загружена и может обрабатывать запросы; проверка жизнеспособности (liveness) — что процесс функционирует. Состояние контейнера `running` и открытый TCP-порт не заменяют функциональной проверки работоспособности.

## 5. Офлайн-воспроизводимость

Офлайн-выпуск содержит образ, веса, токенизатор и шаблон диалога, зависимости, конфигурацию, лицензии и проверочные синтетические примеры. Кэш с однажды скачанной моделью не гарантирует полноту: процесс может попытаться получить конфигурационный файл, пакет или удалённый код. Использование кода из репозитория модели требует отдельного согласования; по умолчанию не следует выполнять произвольный код из такого репозитория.

Манифест связывает артефакты с контрольными суммами. Проверка другой командой на чистой среде обнаруживает скрытые зависимости от домашнего каталога и ручных исправлений. Исходящий трафик и телеметрия проверяются согласно политике предприятия. Том с историей UI также может содержать чувствительные данные; для него нужно определить сроки хранения и порядок удаления.

Секреты передаются способом, согласованным с ИБ; файл `.env` — способ конфигурации, а не полноценное хранилище с ротацией, аудитом и разграничением доступа. Секрет не должен попадать в Dockerfile, слои образа, команды в истории или диагностический вывод.

## 6. Самопроверка с пояснениями

1. Почему модель загрузилась, но следующий запрос вызвал OOM? **Ответ:** выросли контекст, KV-кэш, временные буферы или параллелизм.
2. Что фиксировать кроме имени образа? **Ответ:** digest, источник, версии модели и токенизатора, конфигурацию и проверочные данные.
3. Доказывает ли настройка GPU через `reservations` наличие свободных 12 ГБ? **Ответ:** нет. GPU может использоваться другими процессами, а эта настройка не ограничивает расход видеопамяти.
4. Почему повторный запуск на том же ПК слабее проверки на чистой среде? **Ответ:** локальные кэши и уже созданные файлы могут скрывать отсутствующие артефакты.
