## 1. Слои Windows → WSL2 → Docker → сервер → приложение

WSL2 предоставляет Linux-среду с собственным ядром. Docker Desktop с WSL2 backend управляет контейнерным движком; альтернативой является отдельно настроенный Docker Engine в WSL. Эти пути нельзя бездумно смешивать: разные Docker contexts могут показывать разные образы, volumes и контейнеры. Выбранный путь должен быть единым для группы.

GPU доступен через Windows-драйвер с поддержкой WSL. Внутри контейнера находятся пользовательские CUDA-библиотеки и приложение; образ не заменяет драйвер хоста. NVIDIA отдельно предупреждает об установке Linux GPU-драйвера внутри WSL: используйте правила [CUDA on WSL](https://docs.nvidia.com/cuda/wsl-user-guide/index.html), а не обычный Linux-рецепт. GPU passthrough Docker Desktop для Linux-контейнеров Windows описан в [документации Docker](https://docs.docker.com/desktop/features/gpu/).

Версия CUDA в выводе `nvidia-smi` отражает возможности драйвера, а не доказывает наличие конкретного toolkit в контейнере. Проверка должна проходить по слоям: видимость GPU на хосте, доступ в WSL, доступ из контейнера, загрузка модели, ответ API и оценка ответа. Успешный `nvidia-smi` не доказывает, что inference использует GPU: часть слоёв модели может остаться в RAM/CPU.

Диагностические команды только читают состояние. Первый блок — **PowerShell Windows**, второй — **bash в WSL**; выполнять их для чтения конспекта необязательно.

```powershell
wsl --status
wsl --list --verbose
docker context show
docker version
docker compose version
nvidia-smi
```

```bash
uname -r
nvidia-smi
docker context show
```

При ошибке важно сохранить слой, код ошибки и версию, удалив чувствительные пути и токены. Перезапуск всех компонентов может временно скрыть причину и не является объяснением восстановления.

## 2. Из чего складывается VRAM

Для плотной модели нижняя оценка размера весов — `N × b / 8` байт, где N — параметры, b — бит на параметр. У 8B при 4 битах это 4 млрд байт, около 3,73 GiB. Реальный файл содержит масштабы квантования, метаданные и тензоры другой точности. В памяти дополнительно нужны KV cache, временные буферы, активации и память среды исполнения.

Для обычного KV cache decoder-модели полезна оценка:

`M_KV ≈ 2 × L × B × T × H_KV × D_head × bytes_per_element`.

L — число слоёв, B — одновременно хранимые последовательности, T — токены на последовательность, H_KV — KV-головы, D_head — размер головы. Множитель 2 соответствует ключам и значениям. GQA уменьшает H_KV относительно числа query-голов. Некоторые архитектуры и серверы используют иные схемы хранения, поэтому формула — диагностическая модель, не точный предсказатель.

Стандартная библиотека Python, условная архитектура:

```python
def gib(byte_count):
    return byte_count / (1024**3)


weight_bytes = 8_000_000_000 * 4 / 8
kv_bytes = 2 * 32 * 1 * 4096 * 8 * 128 * 2
print(round(gib(weight_bytes), 2))  # 3.73, только упакованные веса
print(round(gib(kv_bytes), 2))  # 0.50, только KV cache
```

При четырёх последовательностях такой длины KV cache станет около 2 GiB; весам при этом обычно не нужны четыре копии внутри одного процесса. Несколько независимых серверных процессов могут продублировать веса. Реальное число одновременных запросов измеряется вместе с контекстом и выходом.

RTX 3060 12 ГБ ограничивает не только размер весов. Длинный контекст, VLM-изображения и параллелизм способны исчерпать память после успешной загрузки. Для обучения потребуются дополнительные активации, градиенты и состояния оптимизатора — оценка инференса неприменима напрямую. Перед QLoRA обязателен отдельный расчёт из [модуля 8](../08-fine-tuning/self-study.md).

## 3. Квантование и выбор сервера

Квантование представляет веса меньшим числом бит с дополнительными коэффициентами. Уменьшение памяти может сопровождаться потерей качества, особенно на редких терминах, точных числах и следовании схеме. Обозначение «4-bit» не задаёт один алгоритм, точность всех тензоров и размер KV cache.

[GGUF](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) — формат хранения тензоров и метаданных, а не отдельная модель и не универсальный формат обучения. Имя квантования в GGUF нельзя приравнять к NF4 из QLoRA. Совместимость архитектуры, токенизатора и serving проверяется по конкретной ревизии сервера.

Для учебной среды возможны серверы на основе llama.cpp или другие совместимые движки. Выбор зависит от поддержки GPU, формата, моделей, инструментов, схем и офлайн-работы. Не выбирайте сервер только по заявленному throughput на другой GPU. OpenAI-совместимый HTTP endpoint означает сходный транспортный контракт, но не идентичность всех возможностей и значений параметров. Сопоставляются конкретные поддерживаемые поля.

Качество квантованной модели сравнивают с доступным неквантованным или альтернативным baseline на неизменном наборе. Если исходная модель не помещается в учебный ПК, сравнение можно провести на согласованном on-prem резерве. Это ограничение эксперимента фиксируют, а не заменяют утверждением «квантование без потерь».

## 4. Контейнерный контракт и границы доступа

Образ фиксирует программное окружение; volume хранит модели/состояние; сеть задаёт связность. Tag может быть переназначен, digest указывает содержимое образа. Для выпуска нужен digest, а также checksum модели и ревизия токенизатора. Сам по себе digest не доказывает доверенность происхождения образа.

Ниже **иллюстративный Compose-фрагмент**, не готовый стенд. Он предполагает заранее согласованный образ с сервером на порту 8080; переменная `INFERENCE_IMAGE` должна содержать локально доступную ссылку с digest. Команда запуска и health check зависят от этого образа и здесь намеренно не выдуманы.

```yaml
services:
  inference:
    image: ${INFERENCE_IMAGE:?set-approved-image-with-digest}
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - ./models:/models:ro
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```

Синтаксис GPU reservations приведён в [Docker Compose GPU support](https://docs.docker.com/compose/how-tos/gpu-support/). Он запрашивает устройство, но не устанавливает лимит VRAM. Привязка порта к loopback ограничивает доступ с хоста; внутреннюю связность контейнеров, аутентификацию API и исходящий трафик нужно контролировать отдельно. UI не должен открывать незащищённый сервер в сеть предприятия.

Учебный стенд включает inference-сервер, Open WebUI и FastAPI-обёртку. UI нужен для наблюдения, обёртка — для ограниченного контракта, политик и измерений, а не для передачи модели секретов. Readiness означает, что модель загружена и готова, liveness — что процесс жив. Контейнер `running` и открытый TCP-порт не заменяют функциональный health check.

## 5. Офлайн-воспроизводимость

Офлайн-выпуск содержит образ, веса, токенизатор/chat template, зависимости, конфигурацию, лицензии и проверочные синтетические примеры. Кэш с однажды скачанной моделью не гарантирует полноту: процесс может попытаться получить конфиг, пакет или удалённый код. Доверие к remote code требует отдельного согласования; по умолчанию не следует выполнять произвольный код из репозитория модели.

Манифест связывает артефакты с контрольными суммами. Проверка другой командой на чистой среде обнаруживает скрытые зависимости от домашнего каталога и ручных исправлений. Исходящий трафик и телеметрия проверяются согласно политике предприятия. Volume с историей UI также может содержать чувствительные данные и нуждается в retention и удалении.

Секреты передаются способом, согласованным с ИБ; файл `.env` — способ конфигурации, а не полноценное хранилище с ротацией, аудитом и разграничением. Секрет не должен попадать в Dockerfile, слои образа, команды в истории или диагностический вывод.

## 6. Самопроверка с пояснениями

1. Почему модель загрузилась, но следующий запрос вызвал OOM? **Ответ:** выросли контекст, KV cache, временные буферы или параллелизм.
2. Что фиксировать кроме имени образа? **Ответ:** digest, источник, версии модели/токенизатора, конфигурацию и проверочные данные.
3. Доказывает ли GPU reservation наличие свободных 12 ГБ? **Ответ:** нет; GPU разделяется с другими процессами, а reservation не ограничивает память.
4. Почему повторный запуск на том же ПК слабее чистой среды? **Ответ:** локальные кэши и уже созданные файлы могут скрывать отсутствующие артефакты.
