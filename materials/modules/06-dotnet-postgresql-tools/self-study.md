**4 академических часа (180 минут):** .NET/API и секреты — 35 минут; semantic layer и SQL — 45; tool-calling и отказы — 45; подтверждение действий и аудит — 35; самопроверка — 20. Предпосылка — [модуль 3](../03-evaluation-data-security/self-study.md). Достаточно Python/SQL и понимания HTTP; фрагмент C# сопровождается пояснением жизненного цикла клиента.

Цель — уметь проследить, кто и с какими полномочиями получает данные или инициирует действие. Модель предлагает операцию; сервер определяет, допустимо ли её выполнять. Точные версии .NET, схемы БД и механизм аутентификации предприятия пока не заданы.

## 1. Контракт API и идентичность

API-контракт задаёт маршрут, метод, аргументы, типы, единицы, статусы, ошибки, пагинацию и версию. OpenAPI помогает описать форму, но не заменяет предметную семантику: `quantity` может означать заказанное или фактически выпущенное количество. Нужно знать источник истины и момент актуальности.

Аутентификация устанавливает личность, авторизация — допустимость действия над объектом. Сервисная учётная запись приложения не должна незаметно расширять права пользователя. Возможны делегирование пользовательских полномочий и сервисная идентичность с дополнительной проверкой пользовательского scope; реальную схему выбирают совместно с ИБ. Модель не формирует claims, роли и tenant из собственного ответа.

У ресурса проверяются и тип действия, и доступ к конкретному объекту. Право вызвать `get_order` не равно праву читать любой заказ. Сам инструмент проверяет разрешение независимо от решения маршрутизатора. Модель может ошибиться в аргументах или получить внедрённую инструкцию из строки БД.

Секрет-хранилище должно обеспечивать минимальные права, выдачу, аудит, срок действия и ротацию. Переменная окружения — лишь способ доставки в процесс; она не реализует эти свойства. Токен не передаётся в prompt, URL, репозиторий или необработанный exception. Предусматриваются истечение, отзыв и отказ хранилища секретов.

## 2. Клиент .NET и отказы HTTP

.NET — платформа исполнения и библиотеки, C# — один из языков для неё. SDK содержит инструменты сборки, runtime — средства исполнения; установленного runtime недостаточно для компиляции. Проект `.csproj` определяет целевую платформу и зависимости NuGet. Знание Python помогает читать пример: `record` задаёт DTO (объект передачи данных), интерфейс описывает контракт зависимости, а constructor injection передаёт готовый клиент и поставщика токена вместо создания их внутри метода.

`Task<T>` представляет асинхронное завершение с результатом T, `await` ожидает его без блокировки потока в обычном async-пути. `CancellationToken` передаёт запрос отмены вниз по цепочке; отмена не гарантирует откат уже выполненного внешнего действия. Знак `?` у ссылочного типа обозначает возможный null при включённом анализе nullable. `using` освобождает ресурсы запроса/ответа при выходе из области, в том числе при исключении. Эти конструкции важны для надёжности клиента, а не только для синтаксиса.

`HttpClient` управляет соединениями, поэтому создание нового клиента на каждый запрос может истощить ресурсы. Используют согласованный lifetime либо `IHttpClientFactory`; поведение DNS и пулов описано в [HttpClient guidelines](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines).

Ниже **фрагмент для современного .NET** с `System.Net.Http.Json`, внедряемым клиентом и абстракцией поставщика токена. Он предполагает заранее заданный `BaseAddress` тестового API и не реализует корпоративную аутентификацию. DTO условен; для legacy/.NET Framework API и синтаксис сверяются отдельно.

```csharp
using System;
using System.Net;
using System.Net.Http;
using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Threading;
using System.Threading.Tasks;

public sealed record OrderDto(string Id, string Status);

public interface IAccessTokenProvider
{
    Task<string> GetAsync(CancellationToken cancellationToken);
}

public sealed class OrdersClient
{
    private readonly HttpClient http;
    private readonly IAccessTokenProvider tokens;

    public OrdersClient(HttpClient http, IAccessTokenProvider tokens)
    {
        this.http = http;
        this.tokens = tokens;
    }

    public async Task<OrderDto?> GetAsync(string id, CancellationToken ct)
    {
        if (string.IsNullOrWhiteSpace(id) || id.Length > 64)
        {
            throw new ArgumentException("Invalid order identifier", nameof(id));
        }

        using var deadline = CancellationTokenSource.CreateLinkedTokenSource(ct);
        deadline.CancelAfter(TimeSpan.FromSeconds(5)); // пример, не целевой SLA
        using var request = new HttpRequestMessage(
            HttpMethod.Get, "orders/" + Uri.EscapeDataString(id));
        request.Headers.Authorization = new AuthenticationHeaderValue(
            "Bearer", await tokens.GetAsync(deadline.Token));

        using var response = await http.SendAsync(
            request, HttpCompletionOption.ResponseHeadersRead, deadline.Token);
        if (response.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<OrderDto>(
            cancellationToken: deadline.Token);
    }
}
```

Таймаут охватывает получение токена, заголовков и тела. В прикладном сервисе дополнительно ограничивают размер ответа и пагинацию. Запросный заголовок авторизации предотвращает смешение токенов разных пользователей через общие `DefaultRequestHeaders`. Авторизацию объекта выполняет API/инструмент, а не этот транспортный фрагмент. Ошибки 401/403, cancellation, неправильный JSON и недоступность сервиса должны иметь разные внутренние категории.

Ограниченные retries полезны при временном отказе чтения, 429 или некоторых 5xx, с backoff, jitter и общим deadline. 400/403 не исправляются повтором того же запроса. После таймаута записи нельзя знать, произошёл ли эффект: повтор без идемпотентности может создать дубль. Необработанное тело ошибки не отправляется модели и не сохраняется в общий лог.

Проверка `bytes.Length` после `ReadAsByteArrayAsync` обнаруживает слишком большой ответ уже после его загрузки. Для жёсткого ограничения читают поток порциями до лимита плюс один байт; `Content-Length` служит лишь ранней проверкой, поскольку может отсутствовать. Общий deadline действует и при чтении тела, и во время задержки перед повтором. Отмена в такой задержке должна обрабатываться наравне с отменой сетевого вызова. В [исполняемом клиенте](../../practice-kit/dotnet/Client/OrdersClient.cs) эти границы проверяются отдельно от доступности реального API.

## 3. Semantic layer раньше произвольного SQL

Semantic layer предоставляет узкие предметные операции: `get_order_status(order_id)`, `list_shortages(order_id)`. Сервер выбирает заранее подготовленный параметризованный запрос. Это ограничивает пространство ошибок, позволяет явно определить единицы, статусы и допустимые соединения. Произвольный Text-to-SQL оправдан только после измерения, что такой слой не покрывает нужную вариативность.

Параметры защищают **значения**, но не разрешают модели выбирать имена таблиц, SQL-функции или выражения. Идентификаторы и шаблоны выбираются сервером из allowlist. Синтаксически корректный запрос может суммировать строки после неверного JOIN, смешать единицы или выбрать дату создания вместо даты завершения. Это семантическая ошибка, которую компилятор SQL не обнаружит.

Следующий **параметризованный шаблон** предназначен для отдельной учебной PostgreSQL. `$1` и `$2` связывает драйвер, не строковая интерполяция. Он иллюстрирует границы, но не создаёт схему и роли.

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '2s';
SET LOCAL lock_timeout = '500ms';
SELECT order_id, status
  FROM training_api.allowed_order_status
 WHERE order_id = $1
   AND plant_id = $2
 LIMIT 20;
COMMIT;
```

`plant_id` определяется авторизованным контекстом сервера. Значения времени и лимита условны. `READ ONLY` — дополнительный слой, но не защита от раскрытия данных и не запрет всех побочных эффектов функций. Сервисная роль получает только необходимые `SELECT` на согласованные представления; убираются лишние права на схемы, функции, создание объектов и опасные расширения. Правила транзакций описывает [PostgreSQL SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html), таймаутов — [Client Connection Defaults](https://www.postgresql.org/docs/current/runtime-config-client.html).

Row-level security может ограничивать строки, однако владельцы таблиц и роли с обходом RLS имеют особое поведение; см. [Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Для views проверяют права владельца/вызывающего и доступные в закреплённой версии настройки. Нельзя считать наличие RLS в схеме доказательством ограничения конкретной учётной записи.

## 4. Когда SQL всё-таки генерируется

Контур допуска должен разбирать SQL в AST парсером нужного диалекта. Проверяется одно выражение, разрешённый корневой тип, рекурсивно все CTE/подзапросы, таблицы, колонки, функции и операторы. Запрещаются опасные функции, DML/DDL, `COPY`, множественные выражения и обращение к системным объектам вне allowlist. `SELECT` в начале строки, отсутствие `;` и регулярное выражение не являются полноценной проверкой.

AST не заменяет роль БД, разрешённые представления, таймауты и лимиты ресурсов. `LIMIT` сокращает выдачу, но не обязательно стоимость JOIN/сортировки до ограничения. Даже `EXPLAIN` не является разрешением произвольного SQL, а `EXPLAIN ANALYZE` исполняет запрос. Ответы ограничиваются по строкам/байтам и доступности колонок; ошибки схемы не должны автоматически раскрывать модели всю БД.

Семантику оценивают на фиксированных вопросах: верные фильтры, период/часовой пояс, статус, агрегирование, обработка NULL и дублирования JOIN. Совпадение результата на одной маленькой БД может быть случайным, поэтому нужны данные, различающие неверные запросы: одинаковые номера разных заводов, нулевые/отсутствующие значения и несколько позиций заказа. Набор включает неоднозначные вопросы, требующие уточнения.

## 5. Tool-calling как протокол

Tool-calling — выдача моделью имени операции и аргументов согласно схеме. Это ещё не вызов. Dispatcher разбирает ответ, проверяет известное имя, типы, лишние поля, диапазоны и лимиты. Затем инструмент независимо проверяет личность, объект и аргументы. Результат содержит данные и статус, но никогда не становится доверенной инструкцией.

Пример схемы **одного синтетического read-инструмента**, без оболочки конкретного SDK:

```json
{
  "name": "get_order_status",
  "description": "Прочитать статус разрешённого тестового заказа",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "pattern": "^TRN-[0-9]{4}$"}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

Идентификатор вида `TRN-0001` не доказывает доступ. Ограничение шаблона нужно повторить в инструменте, даже если модель работала с constrained output. Схемы версионируются вместе с кодом. Несовместимая смена аргумента должна приводить к контролируемой ошибке, а не неявной записи.

Агент — цикл «получить наблюдение → предложить следующий шаг → проверить и выполнить → вернуть наблюдение». Для него задают бюджет шагов, времени, токенов, вызовов и объёма данных. Неограниченный цикл способен многократно повторять неудачное действие. Для коротких промышленных сценариев явный workflow часто проще проверить, чем свободное планирование.

## 6. Параллелизм, идемпотентность и частичный отказ

Параллельно безопасно выполнять независимые чтения при лимите concurrency и пулов. Зависимый шаг ждёт результат предыдущего. Параллельная запись в один заказ требует предметной синхронизации и контроля версии; ускорение вызовов не должно менять смысл процесса.

Идемпотентность означает сохранение одного логического эффекта повторной операции. Ключ связывают с пользователем/объектом, операцией и hash нормализованных аргументов. Повтор ключа с другим payload отклоняется. Сервер хранит состояние и результат; запись ключа и бизнес-эффекта должна быть атомарной либо согласованной через надёжный протокол. Словарь в памяти процесса не обеспечивает это между перезапусками и несколькими экземплярами.

При таймауте возможен **неизвестный исход**, а не гарантированная неудача. Сначала запрашивают состояние операции по ключу; не повторяют вслепую. Внешние системы обычно не образуют одну транзакцию с локальной БД. Нужны промежуточные состояния, outbox/согласованный workflow и компенсации там, где они предметно допустимы. Компенсация может не восстановить исходную ситуацию полностью.

Аудит связывает trace/request ID, пользователя, версию политики, инструмент, исход проверки и ID эффекта. Секреты и полные SQL-результаты в аудит не попадают. Доступ к подробным следам ограничивается отдельно.

## 7. Предпросмотр и подтверждение write

В курсе любые write выполняются только в изолированном тестовом контуре. Сначала формируется предложение с целевым объектом, текущей версией, полями до/после и последствиями. Человек подтверждает конкретное предложение, а сервер проверяет связь подтверждения с субъектом, payload, версией объекта, сроком действия и одноразовым использованием.

Если заказ изменился после preview, подтверждение устарело: нужна новая проверка и новый предпросмотр. Фраза «согласен» в документе или ответе модели не является подтверждением пользователя. Статический флаг `confirmed=true` в аргументах модели тоже не даёт права записи.

Удобная модель состояний: `draft → validated → awaiting_confirmation → executing → succeeded/failed/unknown`. Из `unknown` выполняют сверку состояния, а не новую неподконтрольную запись. Каждому переходу соответствуют ответственный компонент и событие аудита. Строгая последовательность уменьшает число ситуаций, которые приходится доверять LLM.

## 8. Самопроверка с пояснениями

1. Защищает ли параметризация от выбора неправильного завода? **Ответ:** она защищает значения от SQL-инъекции, но правильность scope и семантики обеспечивает сервер.
2. Можно ли повторить POST после таймаута? **Ответ:** только по согласованной идемпотентности и после выяснения состояния, если исход неизвестен.
3. Достаточно ли имени `read_only_tool`? **Ответ:** фактические права и допустимые эффекты проверяются реализацией и БД.
4. Почему подтверждение привязано к версии объекта? **Ответ:** иначе человек одобрит последствия, уже не соответствующие текущему состоянию.

## Границы учебного эталона

[Комплект](../../practice-kit/README.md) реализует закрытый semantic layer с полным сравнением AST серверного шаблона, отдельной read-only ролью и view A. Такой выбор позволяет изучить контроль SQL, не открывая произвольный генератор запросов. Роль/завод не поступают из ответа модели.

Для эффектов используется локальная SQLite-транзакция: payload/версия/пользователь связаны с preview, эффект и результат сохраняются атомарно, replay переживает новое соединение. Отдельный `workflow.py` запрашивает явное согласие человека; модель его не вызывает. Этот локальный эталон не даёт распределённой транзакции с PDM. Учебный secret volume имеет ограниченные UID/GID-права, но не заменяет корпоративные expiry, отзыв, ротацию и аудит provider.
