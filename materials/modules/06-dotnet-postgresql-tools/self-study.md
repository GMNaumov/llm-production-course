## Маршрут изучения

**4 академических часа (180 минут):** .NET/API и секреты — 35 минут; semantic layer и SQL — 45; tool-calling и отказы — 45; подтверждение действий и аудит — 35; самопроверка — 20. Предпосылка — [модуль 3](../03-evaluation-data-security/self-study.md). Достаточно Python/SQL и понимания HTTP; фрагмент C# сопровождается пояснением жизненного цикла клиента.

Цель — уметь проследить, кто и с какими полномочиями получает данные или инициирует действие. Модель предлагает операцию; сервер определяет, допустимо ли её выполнять. Точные версии .NET, схемы БД и механизм аутентификации предприятия пока не заданы.

## 1. Контракт API и идентичность

API-контракт задаёт маршрут, метод, аргументы, типы, единицы, статусы, ошибки, пагинацию и версию. OpenAPI помогает описать форму, но не заменяет предметную семантику: `quantity` может означать заказанное или фактически выпущенное количество. Нужно знать авторитетный источник данных и момент их актуальности.

Аутентификация устанавливает идентичность, авторизация — допустимость действия над объектом. Сервисная учётная запись приложения не должна незаметно расширять права пользователя. Возможны делегирование пользовательских полномочий и сервисная идентичность с дополнительной проверкой пользовательского scope; реальную схему выбирают совместно с ИБ. Модель не формирует claims, роли и tenant из собственного ответа.

У ресурса проверяются и тип действия, и доступ к конкретному объекту. Право вызвать `get_order` не равно праву читать любой заказ. Сам инструмент проверяет разрешение независимо от решения маршрутизатора. Модель может ошибиться в аргументах или получить внедрённую инструкцию из строки БД.

Секрет-хранилище должно обеспечивать минимальные права, выдачу, аудит, срок действия и ротацию. Переменная окружения — лишь способ доставки в процесс; она не реализует эти свойства. Токен не передаётся в промпт, URL, репозиторий или текст необработанного исключения. Следует предусмотреть истечение срока действия, отзыв и отказ хранилища секретов.

## 2. Клиент .NET и отказы HTTP

.NET — платформа исполнения и библиотеки, C# — один из языков для неё. SDK содержит инструменты сборки, runtime — среду выполнения; установленного runtime недостаточно для компиляции. Проект `.csproj` определяет целевую платформу и зависимости NuGet. Знание Python помогает читать пример: `record` задаёт DTO (объект передачи данных), интерфейс описывает контракт зависимости, а внедрение через конструктор передаёт готовый клиент и поставщика токена вместо создания их внутри метода.

`Task<T>` представляет асинхронное завершение с результатом T, `await` ожидает его без блокировки потока при обычном асинхронном выполнении. `CancellationToken` передаёт запрос отмены вниз по цепочке; отмена не гарантирует откат уже выполненного внешнего действия. Знак `?` у ссылочного типа обозначает допустимость null при включённом анализе nullable. `using` освобождает ресурсы запроса и ответа при выходе из области, в том числе при исключении. Эти конструкции важны для надёжности клиента, а не только для синтаксиса.

`HttpClient` управляет соединениями, поэтому создание нового клиента на каждый запрос может истощить ресурсы. Используют согласованную политику времени жизни либо `IHttpClientFactory`; поведение DNS и пулов описано в [HttpClient guidelines](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/http/httpclient-guidelines).

Ниже приведён **фрагмент для современного .NET** с `System.Net.Http.Json`, внедряемым клиентом и абстракцией поставщика токена. Он предполагает заранее заданный `BaseAddress` тестового API и не реализует корпоративную аутентификацию. DTO условен; совместимость API и синтаксиса с legacy-проектами и .NET Framework проверяют отдельно.

```csharp
using System;
using System.Net;
using System.Net.Http;
using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Threading;
using System.Threading.Tasks;

public sealed record OrderDto(string Id, string Status);

public interface IAccessTokenProvider
{
    Task<string> GetAsync(CancellationToken cancellationToken);
}

public sealed class OrdersClient
{
    private readonly HttpClient http;
    private readonly IAccessTokenProvider tokens;

    public OrdersClient(HttpClient http, IAccessTokenProvider tokens)
    {
        this.http = http;
        this.tokens = tokens;
    }

    public async Task<OrderDto?> GetAsync(string id, CancellationToken ct)
    {
        if (string.IsNullOrWhiteSpace(id) || id.Length > 64)
        {
            throw new ArgumentException("Invalid order identifier", nameof(id));
        }

        using var deadline = CancellationTokenSource.CreateLinkedTokenSource(ct);
        deadline.CancelAfter(TimeSpan.FromSeconds(5)); // пример, не целевой SLA
        using var request = new HttpRequestMessage(
            HttpMethod.Get, "orders/" + Uri.EscapeDataString(id));
        request.Headers.Authorization = new AuthenticationHeaderValue(
            "Bearer", await tokens.GetAsync(deadline.Token));

        using var response = await http.SendAsync(
            request, HttpCompletionOption.ResponseHeadersRead, deadline.Token);
        if (response.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
        response.EnsureSuccessStatusCode();
        return await response.Content.ReadFromJsonAsync<OrderDto>(
            cancellationToken: deadline.Token);
    }
}
```

Таймаут охватывает получение токена, заголовков и тела. В прикладном сервисе дополнительно ограничивают размер ответа и пагинацию. Заголовок авторизации отдельного запроса предотвращает смешение токенов разных пользователей через общие `DefaultRequestHeaders`. Авторизацию объекта выполняет API или инструмент, а не этот транспортный фрагмент. Ошибки 401/403, отмена, некорректный JSON и недоступность сервиса должны иметь разные внутренние категории.

Ограниченные повторные попытки полезны при временном отказе чтения, ответе 429 или некоторых ошибках 5xx; применяют нарастающую задержку, случайный разброс и общий deadline. Ошибки 400 и 403 не исправляются повтором того же запроса. После таймаута операции записи нельзя достоверно определить, был ли применён эффект: повтор без идемпотентности может создать дубль. Необработанное тело ошибки не отправляется модели и не сохраняется в общий лог.

Проверка `bytes.Length` после `ReadAsByteArrayAsync` обнаруживает слишком большой ответ уже после его загрузки. Для жёсткого ограничения читают поток порциями до лимита плюс один байт; `Content-Length` служит лишь ранней проверкой, поскольку может отсутствовать. Общий deadline действует и при чтении тела, и во время задержки перед повтором. Отмена в такой задержке должна обрабатываться наравне с отменой сетевого вызова. В [исполняемом клиенте](../../practice-kit/dotnet/Client/OrdersClient.cs) эти границы проверяются отдельно от доступности реального API.

## 3. Semantic layer раньше произвольного SQL

Semantic layer предоставляет узкие предметные операции: `get_order_status(order_id)`, `list_shortages(order_id)`. Сервер выбирает заранее подготовленный параметризованный запрос. Это ограничивает пространство ошибок, позволяет явно определить единицы, статусы и допустимые соединения. Произвольный Text-to-SQL оправдан только если измерения показывают, что такой слой не покрывает нужную вариативность.

Параметры защищают **значения**, но не разрешают модели выбирать имена таблиц, SQL-функции или выражения. Идентификаторы и шаблоны выбираются сервером из allowlist. Синтаксически корректный запрос может суммировать строки после неверного JOIN, смешать единицы или выбрать дату создания вместо даты завершения. Это семантическая ошибка, которую компилятор SQL не обнаружит.

Следующий **параметризованный шаблон** предназначен для отдельной учебной PostgreSQL. Драйвер связывает параметры `$1` и `$2` со значениями, а не подставляет их строковой интерполяцией. Шаблон иллюстрирует границы, но не создаёт схему и роли.

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '2s';
SET LOCAL lock_timeout = '500ms';
SELECT order_id, status
  FROM training_api.allowed_order_status
 WHERE order_id = $1
   AND plant_id = $2
 LIMIT 20;
COMMIT;
```

`plant_id` определяется авторизованным контекстом сервера. Значения времени и лимита условны. `READ ONLY` — дополнительный слой защиты, но он не предотвращает раскрытие данных и не исключает всех побочных эффектов функций. Сервисная роль получает только необходимые права `SELECT` на согласованные представления; лишние права на схемы, функции, создание объектов и опасные расширения отзываются. Правила транзакций описывает [PostgreSQL SET TRANSACTION](https://www.postgresql.org/docs/current/sql-set-transaction.html), а параметры таймаутов — [Client Connection Defaults](https://www.postgresql.org/docs/current/runtime-config-client.html).

Row-level security может ограничивать доступ к строкам, однако для владельцев таблиц и ролей с обходом RLS действуют особые правила; см. [Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Для представлений проверяют, от имени владельца или вызывающей стороны применяются права, а также настройки, доступные в закреплённой версии. Нельзя считать наличие RLS в схеме доказательством ограничения конкретной учётной записи.

## 4. Когда SQL всё-таки генерируется

Контур допуска должен разбирать SQL в AST парсером нужного диалекта. Проверка должна удостоверять, что запрос содержит одно выражение разрешённого корневого типа, и рекурсивно проверять все CTE, подзапросы, таблицы, колонки, функции и операторы. Запрещаются опасные функции, DML/DDL, `COPY`, множественные выражения и обращение к системным объектам вне allowlist. `SELECT` в начале строки, отсутствие `;` и регулярное выражение не являются полноценной проверкой.

AST не заменяет роль БД, разрешённые представления, таймауты и лимиты ресурсов. `LIMIT` сокращает выдачу, но не обязательно уменьшает стоимость соединения и сортировки до применения ограничения. Даже `EXPLAIN` не является разрешением произвольного SQL, а `EXPLAIN ANALYZE` исполняет запрос. Ответы ограничиваются по числу строк и объёму в байтах, а также по доступности колонок; ошибки схемы не должны автоматически раскрывать модели всю БД.

Семантику оценивают на фиксированных вопросах: верные фильтры, период и часовой пояс, статус, агрегирование, обработка NULL и дублирования строк при соединении. Совпадение результата на одной маленькой БД может быть случайным, поэтому нужны данные, различающие неверные запросы: одинаковые номера разных заводов, нулевые и отсутствующие значения и несколько позиций заказа. Набор включает неоднозначные вопросы, требующие уточнения.

## 5. Вызов инструментов как протокол

Вызов инструмента (tool-calling) — формирование моделью имени операции и аргументов согласно схеме. Это ещё не сам вызов. Диспетчер (dispatcher) разбирает ответ, проверяет известное имя, типы, лишние поля, диапазоны и лимиты. Затем инструмент независимо проверяет личность, объект и аргументы. Результат содержит данные и статус, но никогда не становится доверенной инструкцией.

Пример схемы **одного синтетического read-инструмента**, без оболочки конкретного SDK:

```json
{
  "name": "get_order_status",
  "description": "Прочитать статус разрешённого тестового заказа",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string", "pattern": "^TRN-[0-9]{4}$"}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

Идентификатор вида `TRN-0001` не подтверждает права доступа. Ограничение шаблона нужно повторить в инструменте, даже если модель работала с constrained output. Схемы версионируются вместе с кодом. Несовместимая смена аргумента должна приводить к контролируемой ошибке, а не неявной записи.

Агент — цикл «получить наблюдение → предложить следующий шаг → проверить и выполнить → вернуть наблюдение». Для него задают бюджет шагов, времени, токенов, вызовов и объёма данных. Неограниченный цикл способен многократно повторять неудачное действие. Для коротких промышленных сценариев явно заданный рабочий процесс (workflow) часто проще проверить, чем свободное планирование.

## 6. Параллелизм, идемпотентность и частичный отказ

Параллельно безопасно выполнять независимые чтения при ограничении параллелизма и размеров пулов. Зависимый шаг ждёт результат предыдущего. Параллельная запись в один заказ требует предметной синхронизации и контроля версии; ускорение вызовов не должно менять смысл процесса.

Идемпотентность означает сохранение одного логического эффекта повторной операции. Ключ связывают с пользователем и объектом, операцией и хэшем нормализованных аргументов. Повтор ключа с другим содержимым запроса отклоняется. Сервер хранит состояние и результат; запись ключа и бизнес-эффекта должна быть атомарной либо согласованной через надёжный протокол. Словарь в памяти процесса не обеспечивает это между перезапусками и несколькими экземплярами.

При таймауте возможен **неизвестный исход**, а не гарантированная неудача. Сначала запрашивают состояние операции по ключу и не повторяют операцию вслепую. Внешние системы обычно не образуют одну транзакцию с локальной БД. Нужны промежуточные состояния, outbox или согласованный рабочий процесс и компенсации там, где они предметно допустимы. Компенсация может не восстановить исходную ситуацию полностью.

Аудит связывает идентификаторы трассировки и запроса, пользователя, версию политики, инструмент, исход проверки и идентификатор выполненного действия. Секреты и полные SQL-результаты в аудит не попадают. Доступ к подробным следам ограничивается отдельно.

## 7. Предпросмотр и подтверждение операций записи

В курсе любые операции записи выполняются только в изолированном тестовом контуре. Сначала формируется предложение с целевым объектом, текущей версией, значениями полей до и после изменения и последствиями. Человек подтверждает конкретное предложение, а сервер проверяет связь подтверждения с субъектом, содержимым запроса, версией объекта, сроком действия и одноразовым использованием.

Если заказ изменился после предпросмотра, подтверждение устарело: нужна новая проверка и новый предпросмотр. Фраза «согласен» в документе или ответе модели не является подтверждением пользователя. Статический флаг `confirmed=true` в аргументах модели тоже не даёт права записи.

Удобная модель состояний: `draft → validated → awaiting_confirmation → executing → succeeded/failed/unknown`. Из `unknown` выполняют сверку состояния, а не новую неподконтрольную запись. Каждому переходу соответствуют ответственный компонент и событие аудита. Строгая последовательность уменьшает число ситуаций, которые требуют доверия к решениям LLM.

## 8. Самопроверка с пояснениями

1. Защищает ли параметризация от выбора неправильного завода? **Ответ:** она защищает значения от SQL-инъекции, но правильность области доступа и семантики обеспечивает сервер.
2. Можно ли повторить POST после таймаута? **Ответ:** только по согласованной идемпотентности и после выяснения состояния, если исход неизвестен.
3. Достаточно ли имени `read_only_tool`? **Ответ:** фактические права и допустимые эффекты проверяются реализацией и БД.
4. Почему подтверждение привязано к версии объекта? **Ответ:** иначе человек одобрит последствия, уже не соответствующие текущему состоянию.

## Границы учебного эталона

[Комплект](../../practice-kit/README.md) реализует закрытый semantic layer с полным сравнением AST серверного шаблона, отдельной read-only ролью и представлением для контура A. Такой выбор позволяет изучить контроль SQL, не открывая произвольный генератор запросов. Роль и завод не поступают из ответа модели.

Для эффектов используется локальная SQLite-транзакция: содержимое запроса, версия и пользователь связаны с предпросмотром, эффект и результат сохраняются атомарно, защита от повторного выполнения сохраняется при новом соединении. Отдельный `workflow.py` запрашивает явное согласие человека; модель его не вызывает. Этот локальный эталон не даёт распределённой транзакции с PDM. Учебный том с секретами имеет ограниченные UID/GID-права, но не заменяет корпоративные механизмы управления сроком действия, отзыва, ротации и аудита поставщика секретов.
