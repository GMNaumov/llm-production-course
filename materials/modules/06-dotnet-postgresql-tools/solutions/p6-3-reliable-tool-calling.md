# Эталон П6.3. Надёжный tool-calling

[Задание](../practice/p6-3-reliable-tool-calling.md) · [Теория](../self-study.md) · [Правила сверки](../../../practice-kit/README.md)

Эталон показывает один корректный вариант и границы вывода. Сначала выполните собственную попытку; затем сравните поведение, методику и причины расхождений. Код и таблицы не оценивают работу участника автоматически.

## Разбор решения

Эталонные состояния tool_dispatch: ok, forbidden, dependency_error (не более двух попыток), dependency_error timeout, invalid_arguments. Вредоносная untrusted_note намеренно не становится командой.

Локальные эффекты и idempotency-result записываются одной SQLite-транзакцией BEGIN IMMEDIATE. Повтор токена возвращает прежний результат; payload токена неизменяемый. Для внешнего API это только часть решения: нужны согласованные operation status/idempotency API и сверка неизвестного исхода.

## Как сравнить собственный результат

1. Сопоставьте артефакты с каждым критерием [программы](../../../../curriculum.md) и задания. Укажите доказательство.
2. Разберите хотя бы одно расхождение: методика, набор/версия, ошибка кода, неопределённость или ожидание. Не подгоняйте финальный test под эталон.
3. Подтвердите негативные случаи: Actor=admin в JSON, лишний аргумент, unknown tool, tool output просит write, повтор после timeout. Модель не создаёт новые полномочия.
4. Зафиксируйте ограничения: asyncio.Semaphore ограничивает только один процесс. Для нескольких replicas нужен общий лимит/пул. In-memory cache не доказывает идемпотентность после перезапуска.
5. Передайте отчёт на ручное review. При одиночном прохождении независимая проверка остаётся ожидающей коллегу/преподавателя; собственная сверка её не заменяет.

## Контрольный вопрос

Какие вызовы можно параллелить, а какие изменят смысл сценария при параллельном исполнении?

Итог — аргументированное решение на измеренных данных. Latency/VRAM/стоимость зависят от среды и состава случаев; открытые синтетические результаты не обещают качество предприятия.
