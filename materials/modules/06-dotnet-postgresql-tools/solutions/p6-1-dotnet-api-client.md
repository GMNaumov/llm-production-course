# Эталон П6.1. Подключение к .NET API

[Задание](../practice/p6-1-dotnet-api-client.md) · [Теория](../self-study.md) · [Правила сверки](../../../practice-kit/README.md)

Эталон показывает один корректный вариант и границы вывода. Сначала выполните собственную попытку; затем сравните поведение, методику и причины расхождений. Код и таблицы не оценивают работу участника автоматически.

## Разбор решения

Ожидаемые исходы клиента: 0001→ok, 0403→forbidden, 0503→dependency_error после максимум двух попыток, 0408→timeout_or_cancelled, 9999→not_found. При неверном токене →unauthorized.

Права на read не дают write. Секрет перечитывается provider при запросе; клиент не хранит его в DefaultRequestHeaders/контексте модели. Локальный endpoint моделирует ошибки, но истечение и отзыв корпоративной идентичности проверяются только реальным provider в тестовом контуре.

## Как сравнить собственный результат

1. Сопоставьте артефакты с каждым критерием [программы](../../../../curriculum.md) и задания. Укажите доказательство.
2. Разберите хотя бы одно расхождение: методика, набор/версия, ошибка кода, неопределённость или ожидание. Не подгоняйте финальный test под эталон.
3. Подтвердите негативные случаи: 403 не повторяется; просроченная учётка/отказ provider → отказ; 503 повторяется в бюджете; timeout чтения не становится пустым успешным ответом.
4. Зафиксируйте ограничения: Токен в файле Docker-volume — учебная доставка с ограниченными правами, не полноценное enterprise vault. Для ещё не определённого IdP нельзя придумать OAuth flow и объявить работу промышленно проверенной.
5. Передайте отчёт на ручное review. При одиночном прохождении независимая проверка остаётся ожидающей коллегу/преподавателя; собственная сверка её не заменяет.
