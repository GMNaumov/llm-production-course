# П6.2. Text-to-SQL или semantic layer

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 4 ак. ч. (180 минут). Работа обязательна на базовом уровне. Подготовка — 25 мин; реализация/эксперимент — 80; негативные случаи — 45; анализ и оформление — 30. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Дать модели узкие предметные операции PostgreSQL и проверить смысл результатов и границы SQL.

## Перед началом

П6.1; теория 6, разделы 3–4. Используется отдельная БД training, read-only роль reader_a и view только A.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p6-2-text-to-sql-or-semantic-layer/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`sql/init.sql`, `scripts/sql_client.py`, специально различающие данные: одинаковый TRN-0001 на A/B, available>ordered, available=NULL, injection в status.

## Порядок самостоятельного выполнения

1. Изучите схему и права. Поднимите отдельную учебную БД, дождитесь readiness. Не выдавайте модели admin/service password; read-role видит только allowed_orders_a, базовая orders ей недоступна.

2. Реализуйте операции status/shortage через серверный allowlist и параметры. AST guard эталона допускает только полный AST одного из шаблонов; ввод произвольного SQL исключён. Если выбираете Text-to-SQL, расширьте рекурсивный guard и отдельно обоснуйте необходимость.

3. До прогона составьте вопросы и эталоны: дефицит 0001 A=6 шт., 0002 A=0, для 0003 неизвестно из-за NULL, 0004 статус содержит недоверенную строку. Выбор завода берётся из серверной личности/роли.

4. Проверьте AST на несколько statements, CTE/DML, pg_sleep, системные таблицы, SELECT INTO, подзапрос и замену view. Попытки вне точного шаблона должны отклоняться до БД. В БД отдельно проверьте write/base-table denial, timeout и ограничения ответа.

5. Оцените семантическую правильность на фиксированных вопросах: NULL не равен нулю, surplus не отрицательный дефицит, единицы не смешиваются, B не участвует. Сохраните аудит ID операции/исхода без SQL-результатов.

```powershell

```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

`SELECT ...; DROP ...`, UNION к secret таблице, pg_sleep, чужой завод, инструкция внутри status. Невалидный запрос не исполняется, данные не превращаются в SQL.

## Самопроверка и критерии приёмки

используются отдельная БД/схема, read-only роль, allowlist, AST-проверка, запрет множественных и небезопасных выражений, лимиты строк/времени/ресурсов и аудит; на фиксированном наборе оценена семантическая правильность, а не только синтаксис; тесты на вредоносный текст в данных и обход ограничений пройдены.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

SQL/schema/role manifest, allowlist/AST код, вопросы с эталонами, построчные semantic/security результаты и лимиты.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

PostgreSQL GREATEST с NULL имеет особые правила; эталон явно исключает available IS NULL. Пустой результат для 0003 нужно преобразовать в «данных недостаточно», а не «дефицита нет». LIMIT не ограничивает стоимость произвольного JOIN.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
