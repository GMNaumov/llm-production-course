# П6.1. Подключение к .NET API

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 3 ак. ч. (135 минут). Работа обязательна на базовом уровне. Подготовка — 20 мин; реализация/эксперимент — 60; негативные случаи — 35; анализ и оформление — 20. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Реализовать ограниченный .NET HTTP-клиент с управлением отказами и жизненным циклом учётных данных.

## Перед началом

Теория 6, разделы 1–2; П3.3. Сначала локальный .NET API комплекта, затем согласованный тестовый API предприятия без выдумывания его схемы/auth.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p6-1-dotnet-api-client/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

`dotnet/Api`, `dotnet/Client`; тестовые ID 0001, 0403, 0503, 0408, 9999. Секреты Docker-volume создаются secrets-init с UID/GID-доступом; корпоративное хранилище подключается отдельным provider.

## Порядок самостоятельного выполнения

1. Прочитайте API-контракт и роли. Поднимите secrets-init, db/api по README. Составьте матрицу прав: сервис, пользователь, объект, read/write. Учебный API — только read и не заменяет корпоративную аутентификацию.

2. Соберите клиент в .NET SDK по инструкции комплекта. Используйте долгоживущий HttpClient, per-request Authorization, escaping ID и единый deadline получения токена/заголовков/тела. Запишите ограничения размера ответа и пагинации.

3. Выполните штатный read, 403, 503 с ограниченным повтором, 404 и timeout. Добавьте отсутствие/неверный токен, отмену и некорректный JSON. Ошибки не раскрывают токен/тело исключения пользователю или LLM.

4. Для учебной ротации используйте отдельную копию стенда и новый provisioned secret; не меняйте действующие учётные данные предприятия. В корпоративном отчёте опишите provider, срок, отзыв, аудит, ротацию и поведение при недоступности хранилища с владельцем ИБ. Одних env vars недостаточно.

5. Подключите разрешённый тестовый API предприятия при выданном контракте. Если его нет, зафиксируйте локальную проверку и незакрытую интеграционную часть. Минимальные права и согласованный lifecycle секретов нельзя доказать синтетической заглушкой.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm secrets-init
docker compose --profile integration up -d --wait db api
# Сборка/запуск .NET Client — по README комплекта (копия в /tmp контейнера).
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Проверьте тело больше лимита с `Content-Length` и без него. Клиент должен остановить чтение на лимите плюс один байт. Отмените запрос во время задержки перед повтором и различите отмену пользователя, таймаут и транспортный отказ. Подставной HTTP-handler воспроизводит эти границы без изменения API.

403 не повторяется; просроченная учётка/отказ provider → отказ; 503 повторяется в бюджете; timeout чтения не становится пустым успешным ответом.

## Самопроверка и критерии приёмки

права минимальны; секреты хранятся и ротируются согласованным с ИБ способом, а не только переменными окружения; проверены отказ доступа, истечение учётных данных, таймаут и повторный запрос; секреты отсутствуют в коде и логах.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

клиент/provider, матрица прав, очищенные результаты HTTP/timeout/retry, схема ротации/отзыва и раздел корпоративной интеграции.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

Токен в файле Docker-volume — учебная доставка с ограниченными правами, не полноценное enterprise vault. Для ещё не определённого IdP нельзя придумать OAuth flow и объявить работу промышленно проверенной.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
