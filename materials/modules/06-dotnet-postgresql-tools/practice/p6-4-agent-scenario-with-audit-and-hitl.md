# П6.4. Агентный сценарий с аудитом и HITL

[Теория](../self-study.md) · [Обзор](../README.md) · [Программа](../../../../curriculum.md)

**Объём:** 5 ак. ч. (225 минут). Работа обязательна на базовом уровне. Подготовка — 35 мин; реализация/эксперимент — 100; негативные случаи — 55; анализ и оформление — 35. Образы и модели организатор готовит заранее; время скачивания сюда не входит.

## Задача и результат

Собрать законченный тестовый workflow поиска заказа, проверки спецификации и подтверждённого изменения.

## Перед началом

П5.2/П5.4, П6.1–П6.3; теория 6, разделы 6–7. Запись только в локальную синтетическую БД или специально разрешённый тестовый контур.

Для автономного выполнения используйте [учебный комплект и инструкции запуска](../../../practice-kit/README.md). Команды выполняются в **PowerShell из каталога `materials/practice-kit`**. Свои изменения/результаты храните в `work/p6-4-agent-scenario-with-audit-and-hitl/`, сохраняя исходники эталона. Используйте [шаблон отчёта](../../../practice-kit/templates/report.md) и [протокол оценки](../../../practice-kit/templates/protocol.md).

## Исходные данные

TRN-0001 A quantity=10/version=1, спецификация с источником, `tools.py` и сохранённые read-результаты. Preview/confirm вызываются отдельно человеком, а не моделью.

## Порядок самостоятельного выполнения

1. Составьте явный workflow максимум из согласованного числа шагов: read order → read specification → validate units/source → propose change → preview → ожидание человека → confirm. Разделите права read/write и места транзакций.

2. Покажите человеку старое/новое количество, единицу, объект, версию и последствия. Создайте ограниченный по времени одноразовый confirmation_id, привязанный к actor/plant/payload/version. Модель не видит и не подтверждает этот токен.

3. Реализуйте человеческий шаг отдельным CLI/UI: по умолчанию отказ, подтверждается конкретный preview. Булево поле из ответа модели не является согласием человека.

4. Проверьте отказ пользователя, подмену объекта/actor, устаревший preview после изменения версии, истёкший токен, повтор после рестарта и два одновременных confirm. Сверьте actual state, а не только текст ответа.

5. Сымитируйте разрыв после commit до получения ответа. Сверьте состояние по confirmation_id и верните сохранённый результат. Для внешнего PDM опишите outbox/unknown outcome/компенсацию с владельцем; не выдавайте локальную транзакцию за распределённую.

## Команды для воспроизводимого старта

```powershell
docker compose run --rm lab python scripts/demo.py effects
# Интерактивный эталон отдельного человеческого шага:
docker compose run --rm -it lab python scripts/workflow.py
```

Команды запускают эталонные компоненты/измерения. Скопируйте результаты из `work/` в каталог своего прогона до повторного запуска. Это инженерная проверка поведения, а не автоматическая сдача задания.

## Негативные случаи

Нет явного согласия, иной actor/объект/версия, повтор после timeout, неверная единица, недоступная спецификация. Не должно быть неподтверждённого эффекта.

## Самопроверка и критерии приёмки

чтение и запись разделены; перед write показываются последствия и требуется явное подтверждение; есть трассировка, границы транзакций, поведение при частичном отказе и защита от повторного выполнения; производственная запись исключена.

Для каждого пункта укажите артефакт/строку результата в [листе ручного review](../../../practice-kit/templates/review.md): выполнено / требуется исправить / недостаточно данных. Пороги фиксируются до финального теста по риску и baseline; демонстрационные числа не являются нормами предприятия. Все ошибки и отрицательные результаты остаются в отчёте.

## Что представить для сверки

workflow и человеческий интерфейс, state machine, preview/confirm протокол, аудит и матрица replay/stale/partial failures.

Укажите версии кода/конфигурации/модели/данных, происхождение выборки, baseline, ограничения, негативные результаты и индивидуальный вклад. Для неприменимой метрики напишите причину, не ставьте ноль. Результат проверяет человек; исправление и повторное review допускаются.

## Если результат не получается

demo.py программно демонстрирует оба состояния для эталона и не является реальным подтверждением пользователя. В собственной работе подтвердить должен человек через отдельный шаг, не агент.

Сохраните минимальный синтетический пример, определите слой сбоя и повторите один случай. Не меняйте сразу модель, данные и порог: иначе причина останется неизвестной. Недоступная корпоративная зависимость остаётся явным пробелом проверки.
